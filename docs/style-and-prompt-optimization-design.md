> 版本：v1（设计提案）｜日期：2026-09-22
> 范围：Agent 资产 / 多 Agent 编排 / Prompt 与上下文 / 输出风格（去 AI 腔）/ 评测闭环
> 前置阅读：design.md（架构总纲）、agents/_protocol.md（全局协议）

## 0. 背景与诊断

### 0.1 现状盘点（已核实）

| 层 | 现状 | 评级 |
| --- | --- | --- |
| Agent 资产 | 44 场景 / 165 角色，六段骨架 100% 达标，场景协议含质量红线 | 专家级（结构） |
| 编排 | 波次调度 + 四层循环检测 + fan-in 收敛 | 专业级偏上 |
| 上下文 | L0–L5 分层装配、前缀缓存保护、回合组原子截断 | 专业级偏上 |
| 质量验证 | 32 项 eval 基线全绿，但**全部是 mock 模式** | 不达标（行为质量无门禁） |
| 输出风格 | 仅 5/165 角色有灵魂文件；协议强制分点 + 200 字 + 固定收尾 | **AI 腔重灾区** |

### 0.2 「AI 腔」的来源解剖

输出的 AI 味不是模型问题，是**协议与人设共同塑造的必然结果**。逐条定位：

1. **全局协议强制分点**（`_protocol.md` role_contract：「用 Markdown 分点表达」+ 200 字上限）
   → 所有角色说话都是「- 要点1 - 要点2 - 要点3」，165 个角色共用一种文体。
2. **固定收尾模板**：协议要求收尾按「已完成 / 待确认 / 下一步」汇总；投研等场景强制免责声明；
   深度档要求「每章以结论句收尾」→ 每篇产出结尾都长得一样。
3. **结构化崇拜**：交付规格表（字数/章节/来源数/图表数门槛）+ 回合指令的命令式列表
   → 模型学会了「先交骨架、再填满格子」，内容成了填表。
4. **灵魂覆盖率 3%**（5/165 角色）：soul 的设计（表达示例 / 口头禅库 / 互动偏好）正是解药，
   但 162 个角色没有这一层，全靠「你是 XX 师，白板旁立着 YY」一句人设撑风格。
5. **零 few-shot**：协议全是命令式规则（「不要」「禁止」「必须」），没有一个「好的发言长什么样」的
   正例。负面约束只能防烂，不能育好。
6. **回合指令复述纪律**（每轮重注「全程简体中文」「行首 @ 才生效」）是必要的冗余，但也强化了
   「按清单作答」的机器感。

### 0.3 优化总目标

| # | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | 对话发言「像人」：不同角色有可辨识的文风，减少分点依赖、模板收尾 | judge rubric 新增 AI 腔维度 ≥4/5 |
| G2 | 交付件「像专家写的」而非「按规格填的」：结构服务内容，不一刀切 | 深度报告人工盲评通过率 |
| G3 | Prompt 成本与专注力：按场景裁剪协议，system token 降 20–35% | 装配层 token 计量对比 |
| G4 | 行为质量有门禁：eval 从 mock 机制断言升级到内容级断言 + judge 分数基线入 CI | CI 可红 |
| G5 | 转交可靠性：handoff 结构化通道升格为权威，@ 解析降级 | 弱模型探针接力成功率 |

原则：**零行为回退**——所有改动默认对存量场景透明，新能力显式 opt-in；协议文本改动必须过 eval 基线门禁。

## 1. 改造一：协议分层裁剪（G3）

### 1.1 问题

全局协议 11KB 一刀切注入全部角色：塔罗师被要求读「git 六件套 / worktree / ALLOWED_ROOTS」，
厨师被要求读「定时任务三件套」。后果：每回合 ×165 角色的 token 浪费 + 指令稀释（instruction dilution，
约束越多每条越不被遵守）。

### 1.2 设计：协议段标记 + 场景裁剪清单

**步骤 1：给 `_protocol.md` 的段落打能力标签**（不改语义，只加结构）：

```markdown
<tool_policy scopes="file,git,web,business,schedule">
  <segment scope="file">…文件工具纪律（全场景保留）…</segment>
  <segment scope="git">…git 六件套 / worktree / ALLOWED_ROOTS（仅仓库类）…</segment>
  <segment scope="web">…联网检索降级链（有 web_search 的角色）…</segment>
  <segment scope="business">…calc / date_calc / csv_analyze / template_fill（业务类）…</segment>
  <segment scope="schedule">…schedule_task 三件套（默认裁剪，需要时由工具发现引导）…</segment>
</tool_policy>
```

**步骤 2：裁剪依据 = 角色自己的 front-matter `tools` 列表**（单一事实源，零新增配置）：

- `tools` 含 `git_*` → 保留 git 段；否则裁剪；
- 含 `web_search` → 保留 web 段；
- 含 `calc/csv_analyze/template_fill` 任一 → 保留 business 段；
- 定时任务段**默认裁剪**（协议已引导 `tool_search` 激活，发现机制已存在，段文本只在工具真实加载后由工具描述承担）。

**步骤 3：装配层实现**（`context/assembler.ts` / `store/prompts.ts`）：

```ts
// prompts.ts：解析 segment 标签 → 结构化协议
export interface ProtocolDoc { full: string; segments: Map<Scope, string> }
// assembler.ts buildSystemPrompt：按 agent.tools 计算保留 scope 集，拼装 L0
```

无 `segment` 标记的旧协议文件按全量注入（向后兼容）。

### 1.3 连带裁剪

- `<deliverable_spec>` 四档规格表**移出常驻 system**：改为「用户声明档位时由回合指令注入全文」
  （`buildSpecInstructionLine` 已存在，扩展为携带规格表全文）；未声明时人设的「交付契约」段
  已含默认档，足够。
- AGENT.md 正文中的工具纪律（「金额必须 calc」类）与全局协议去重：全局管通用，人设只留独特判断。
  由 check:agents 新增「重复段落检测」软告警驱动渐进收敛，不强制一次改完。

### 1.4 预期收益

塔罗/生活类角色 system 缩减约 30–35%；研发类约 15–20%。指令密度下降 → 每条纪律更「贵」。

## 2. 改造二：去 AI 化风格系统（G1、G2）——本次设计的核心

### 2.1 设计原则

1. **风格是资产，不是祈祷**：像六段骨架一样，文风必须落成可校验的文件，不写进协议靠模型自觉。
2. **分场景分级**：交付件可以结构化（专家报告本来就有体例），**对话发言必须去模板化**。
3. **正例优先**：每个风格单元必须带「好的例子」，负面清单只做底线。
4. **零回退**：无风格资产的角色行为与现状完全一致。

### 2.2 资产结构：Voice（声纹）文件

为每个角色新增可选文件 `agents/<场景>/<角色>/voice.md`（与 souls/ 平级、正交——
soul 管人格，voice 管文风；soul 在场时 voice 为其提供基线文风，soul 可覆盖语气）：

```markdown
---
id: voice
---
## 说话方式
- 默认连段成文，2–4 句一段；只在「列举项 ≥3 且互不相关」时才分点。
- 有自己的切入习惯：先说你最在意的那件事，不从「好的 / 收到 / 我来」开头。
- 收尾停在具体动作上（下一棒 / 一个问题 / 一个文件路径），不总结陈词。

## 句式偏好
- 长短句混用；允许插入语和反问；数字落在句子里（「预算 4 万，砍到 2.8 万能保住 P0」）。
- 禁用词表：综上所述 / 总而言之 / 赋能 / 抓手 / 闭环 / 打磨 / 颗粒度（场景专业术语除外）。

## 示例（好的发言）
> 看完前端那版了。登录失败锁定的口径和 PM 文档对不上——文档写 5 分钟，实现是 10 分钟。
> 我按文档口径提了 issue，@费利 你确认下以哪个为准，我这边用结论补用例。

## 反例（AI 腔，禁止）
> - 已检查实现与文档差异 ✅
> - 发现锁定时间不一致问题
> - 下一步：待 PM 确认后更新用例
```

**校验**：`check:agents` 新增 voice 报告（存在性 + 必须有「示例」段 + 禁用词表非空为达标），
同灵魂一样报告模式先行，达标率上来后转 strict 门禁。

### 2.3 分层输出契约（改写 `_protocol.md` role_contract）

现状「分点 + 200 字」一刀切 → 改为**三通道文体契约**：

| 通道 | 文体 | 约束 |
| --- | --- | --- |
| 对话发言（气泡） | **段落优先**：默认连贯短文；分点仅在「≥3 个互不相关项」时允许 | 软上限 300 字，超限建议落盘 |
| 交接/汇报（收尾棒） | 结构化保留（「已完成/待确认/下一步」是真需求） | 每格一句话，禁止把正文内容重复一遍 |
| 交付件（工作区文件） | 按人设交付契约 + 用户声明档位 | 「每章结论句收尾」从强制降为**建议**；允许作者按内容选体例 |

配套删除/弱化：
- role_contract 的「用 Markdown 分点表达」改为「分点服务于清单，不服务于表达」；
- `<output_contract>` 增加**通用 AI 腔禁用词表**（连接词类：首先/其次/再者/综上所述/总而言之；
  动词类：赋能/助力/聚焦（滥用时）；收尾类：希望对你有帮助/如有问题随时提问）；
  场景协议可追加自己的词表（合并生效）。

### 2.4 灵魂系统扩编（5/165 → 全覆盖）

voice 解决「文体」，soul 解决「人格」。当前 162 个角色无人格层，是腔调趋同的第二大来源。

- **不追求每角色多灵魂**：先给每个角色 1 个默认 soul（从 AGENT.md 人设正文里蒸馏：
  那句「工位旁立着白板」式的描述扩成 tone/traits/quirks + 2–3 条表达示例）；
- **批量生成 + 人工抽检流程**：用脚本从 AGENT.md 抽取初稿 → check:agents 校验结构 →
  eval judge 抽检「同题异角色」输出区分度（见 §4.3）；
- 优先级：用户高频场景先行（development / research / invest / brainstorm / 生活类），
  长尾巴场景可暂缓，voice.md 已能兜底文体。

### 2.5 回合指令去机器感

- 命令式列表保留（可靠性需要），但**增加 1 条语音示例行**（当角色有 voice/soul 时）：
  `- 你的语气参考：「兄弟们，我有个疯狂的想法——」（节选自你的声纹，保持这个味道，不要念出来）。`
- 范例从 voice.md 的「示例」段随机取 1 条注入（每回合轮换，防过拟合单一例句）；
- 「全程简体中文」「行首 @」等纪律行**合并为一行**，降低清单感（机制不变）。

### 2.6 温度与采样分通道

front-matter 已有 per-role `temperature`。细化：

- 对话发言：voice/soul 在场时 +0.1（风格化需要发散度，上限 0.8）；
- 交付件写入（检测到 write_file 参数的回合）：不额外调整（事实密度优先）；
- 纯调度回合（只转交）：−0.1。
实现于 engine 的 provider 调用处，配置开关 `VOICE_TEMP_BOOST=true`（默认开，可关）。

## 3. 改造三：转交与编排可靠性（G5）

### 3.1 handoff 升格为唯一权威通道

现状双通道（行首 @ 正则 + handoff 工具）并存，弱模型失效面大。

- 引擎侧：**handoff 工具的 structured output 为转交的唯一事实源**；
  @ 正则解析保留，但仅用于（a）渲染接力链 UI，（b）模型没调 handoff 时的降级兜底（现状行为）；
- 协议侧：`_protocol.md` 改为「需要队友接手 → 调 handoff 工具；正文里的 @ 只是给观众看的标注」；
- 观测：trace 增加 `handoff_channel: tool|text` 字段，上线后看 text 占比，目标 <10%；
- 兼容：双通道并行至少一个里程碑，eval 全绿后才改协议文案。

### 3.2 fan-in 收敛对账（轻量版）

并行波结束后，引擎在下一棒的回合指令追加**对账清单**（零模型成本，纯系统注入）：

```
- 上一波并行产出对账（请确认均已纳入你的汇总，缺漏请显式说明）：
  · 雷动：docs/技术面-XX.md（写入 3.2KB）
  · 闻笛：未落盘文件（纯发言）
```

数据来自已有的 write-tracking（M61 已实现波级写计数），此处只是把摘要显式喂给收敛方。

### 3.3 critic 环节（opt-in，不进默认链）

- 计划范式已有 review；补一个更轻的「交付前互检」：场景 `_group.yaml` 新增
  `review_before_return: true`（如 invest / research 开启）→ 交还用户前自动插入一次
  审查波（由与作者不同的成员执行 review 范式）；
- 默认关，避免全链路成本翻倍。

### 3.4 引擎拆分（工程化，不赶本次里程碑）

`engine.ts` 3931 行拆为：`wave-runner.ts`（波次循环）/ `tool-loop.ts`（工具循环+审批）/
`run-transport.ts`（SSE/WS）/ `run-state.ts`（状态机）。纯重构，行为零变化，eval + 全量测试兜底。
单独立项，不与协议改动同批。

## 4. 改造四：评测闭环升级（G1–G5 的验收底座）

### 4.1 内容级离线断言（不需要真实模型，先进 CI）

eval runner 新增断言类型（全部离线可判）：

```json
{ "type": "artifact_min_chars", "path": "docs/投研报告-X.md", "value": 4000 }
{ "type": "artifact_contains", "path": "...", "values": ["免责声明", "asOf"] }
{ "type": "message_no_banned_words", "values": ["综上所述", "赋能"] }
{ "type": "message_bullet_ratio_lte", "value": 0.6 }
{ "type": "handoff_channel", "value": "tool" }
```

`bullet_ratio`（分点行占比）与禁用词是 AI 腔的可机检代理指标——不完美，但能让回归立刻可见。
首批给 38 个任务中 10 个补上内容断言。

### 4.2 judge 基线入库 + CI 门禁

- 夜间跑 `--judge`，rubric 增加两个维度：
  - **AI 腔评分**（1–5）：分点依赖度 / 模板收尾 / 禁用词 / 文风口吻一致性；
  - **角色区分度**（1–5）：遮住角色名能否认出是谁（judge 同时看两个角色的同题输出打分）；
- 分数基线存 `evals/judge-baseline.json`，跌 >0.5 分红 CI（夜间 job，不阻塞 PR）；
- mock 基线保留（机制回归的第一道网）。

### 4.3 风格专项探针任务

新增 6 个 eval 任务专测文风：

1. `voice-no-bullets`：生活场景闲聊式提问，断言 bullet_ratio ≤ 0.3 且无禁用词；
2. `voice-distinct`：同一问题分别问 3 个角色，judge 打区分度；
3. `handoff-tool-channel`：断言转交走工具通道；
4. `report-structure-freedom`：深度报告不再强制每章结论句（断言无「综上所述」且 judge ≥4）;
5. `soul-consistency`：带灵魂角色切换灵魂后文风可感知变化（judge 对比）；
6. `parallel-reconciliation`：并行波收敛方对账完整性。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 协议裁剪误伤（某角色需要被裁掉的纪律） | 行为回退 | 裁剪依据是 front-matter tools（权责同源）；eval 全量 + 报告模式观察一个里程碑 |
| voice 示例过拟合（所有发言都像例句） | 新模板腔 | 每回合轮换注入示例；judge 区分度维度监控；示例库每角色 ≥3 条 |
| 禁用词表误伤专业术语 | 报告变怪 | 场景协议可豁免（「闭环」在研发场景是术语）；词表分「全局禁用 / 场景豁免」两级 |
| handoff 权威化后弱模型不调工具 | 接力断裂 | 保留 @ 解析降级兜底（只是不再权威）；双通道并行观察期 |
| 风格化牺牲信息密度 | 交付变水 | 分层契约保交付件结构；交付件 AI 腔约束只禁「空洞套话」不禁体例 |
| judge 评分不稳定 | CI 误红 | 基线取 3 次中位数；阈值留 0.5 缓冲；红时附完整 trace 供人工复核 |

## 7. 不做的事（显式排除）

- 不引入多模型投票 / 混合专家路由（成本与复杂度不匹配当前阶段）；
- 不改并行波上下文隔离语义（对账是注入摘要，不是打通实时可见）；
- 不为每角色追求多灵魂（先一人一格，扩编是 P4 持续工作）;
- 不动 L0–L5 装配分层结构本身（已验证有效，只做裁剪与注入内容调整）。

## 8. 附录：owli-code《长任务 Code Agent 设计》借鉴评估（2026-09-22，v2 修订）

参考文档：`docs/reference-owli-code-design.md`（外部文档的只读副本，非本仓库设计事实源）。该系统是**单 Agent 长任务编码**场景，与本项目「多角色会话协作」不同构。

**v2 修订说明（评审反馈后重估）**：v1 对 Spec 锚定类设计评估偏乐观。对方系统的骨架是「Spec 冻结锚点 → 逐条验证 → 按 Spec 折叠上下文」，而本项目的计划（write_plan）是 opt-in 的轻量协作约定——多数 Run 无计划、无「可机检验收方法（test）」概念，**所有以 Spec 为锚点的设计在本项目缺少落点**。以下按修订后结论呈现；Prompt 版本化与成本预算门按评审决定移除（理由见 8.3）。

### 8.1 建议借鉴（与编码域无关、在本项目有真实落点）

| 设计 | 对方做法 | 我们的落点（修订后） |
| --- | --- | --- |
| **确定性中间件框架**（§8） | 每轮循环末尾跑「系统状态触发」的规则，**关键动作不依赖 LLM 自觉** | 框架思想与编码域无关，借鉴的是**机制**而非其具体规则（自动提交/锁文件同步是编码域规则，不移植）。新建 `wave-middleware.ts` 波末规则框架，首批规则全部面向协作域：①交付件规格机检（write_file 后离线校验字数/章节/禁用词，不达标注入返工提示）；②fan-in 对账注入（§3.2）；③并行波全员沉默时自动收口（现 fallback 逻辑迁入统一管理） |
| **关键消息标记**（§3.3 `markCritical`） | 用户澄清/纠正、关键决策永不压缩 | assembler L4 窗口：用户消息一律标记 critical，回合组裁剪时 critical 组豁免丢弃。解决「窗口截断把用户中途的口径纠正丢掉」的真实风险。不学其内容正则实现，用角色位标记 |
| **主动收尾**（§3.4 `shouldWrapUp`） | 迭代进度 × 任务进度 × 时间预算，不足即主动收口部分交付 | **去 Spec 化重写**：进度信号不锚定计划完成度，改用本项目已有的领域信号——波数进度 × 波级写产出计数（write-tracking 已有）× 停滞检测（M61-D3 已有）。「波数 >80% 且近 N 波零写产出 → 注入收口指令，强制部分交付 + 剩余清单」。避免 `maxTurnsPerRun` 硬截断时连汇总都没有 |

### 8.2 选择性借鉴（剥离编码域锚点后改造）

| 设计 | 修订后评估 |
| --- | --- |
| 「证据强制」原则（§16.1 独立验证器） | **只取原则，不取架构**。对方的「Spec→测试映射」「独立 LLM 会话验收」都锚定在「验收方法 = 跑测试」这一编码域前提上，本项目 165 个角色里仅研发场景有此概念。保留的仅是：review 范式的 `submit_review` pass 必须挂 evidence（已部分存在，收紧为强制），以及 §4.1 的离线内容断言（断言逻辑由 eval runner 承担，不需要运行时验证器） |
| 意图引擎「假设提取」（§12.1） | 复述确认三段式对多角色会话太重；假设提取零成本融入 PRS 路由：派发指令里显式列「假设：…（被推翻请纠正）」 |
| 反思节律（§19.2，每 10 轮反思） | 不单设节拍；合并进滚动摘要触发时机，由收口成员输出「反思三行」进 L2 |

### 8.3 不建议借鉴 / 评审移除

- **Spec 冻结锚点体系整体**（§2/§5.2/§12.1 generateSpec/§16 验证器主体）：对方是「一个任务 = 一组可机检 Spec」的编码世界；本项目是多角色开放式协作，产出形态（报告/方案/对话/牌阵）大多无「可机检验收」，强行引入等于把框架扭成编码工具。**评审结论：不移植**；
- **按完成度折叠**（§3.3 `foldCompleted`）：锚定 Spec 状态，无计划 Run 完全不生效；本项目 L4 已有「回合组原子裁剪 + critical 豁免」（8.1 第 2 条），边际收益不抵复杂度。**评审结论：不移植**；
- **Prompt 版本化**（§19.3）：**评审决定移除**。本项目协议/人设即仓库内文件，git 历史天然是版本系统；judge 回归归因直接用 git commit 即可，再建一套 `PROMPT_VERSION` 切换是重复造轮子；
- **成本预算门**（§7.3）：**评审决定移除**。本项目是本地单用户应用，成本约束不是一等需求；usage 落库已支持事后核算，运行时 budget 门的 ROI 过低；
- **Repo Map / code-intel Python 服务**（§6/§15）：重资产代码索引，只服务研发场景，需要时以 MCP 外接；
- **子 Agent 派生体系**（§14）：单 Agent 裂变并行编码的模式；本项目协作单元就是平权角色成员，并行波已覆盖，无派生需求；
- **写后自动 lint / 自动测试**（§16.2 等编码域规则）：不进入通用框架；研发场景未来如需，作为 wave-middleware 的一条场景级规则开启。

### 8.4 反向发现（对方设计提示我们已做对的）

对方 9.1 修订记录暴露的坑，我们已规避或需引以为戒：压缩重排破坏前缀缓存（我们 L0 字节级稳定 + 运行时上下文天级稳定，✓ 已防）；猴子补丁式 Plan Mode 拦截可被绕过（我们工具白名单是范式边界，✓ 同思路）；折叠依赖不存在的参数导致永不触发（教训：**任何「状态→行为」联动都要有 eval 断言证明它真的会触发**——已并入 §4.1 断言设计）。

### 8.5 修订后的最终移植清单

从 v1 的 7 项收敛为 **3 项**，全部无编码域依赖：

1. **确定性中间件框架**（波末规则；首批：交付件机检 / fan-in 对账 / 沉默收口）→ 并入 P1/P5；
2. **用户消息 critical 豁免裁剪** → 并入 P0（随装配层改动一并落地）；
3. **去 Spec 化的主动收尾**（波数 × 写产出 × 停滞三信号）→ 并入 P5。
