# ADR 0116：纪要容器（`::: minutes`）内 @ 不参与转交解析（M42）

- 状态：Accepted
- 引入：M42
- 相关：[design.md §71.5](../design.md)、ADR 0115（圆桌会议范式）、ADR 0004（交还判定：仅行首 `@用户`）、ADR 0034（Markdown 容器语法）、[server/src/orchestration/parser.ts](../../server/src/orchestration/parser.ts)、[server/tests/parser.test.ts](../../server/tests/parser.test.ts)、[server/tests/m42-meeting.test.ts](../../server/tests/m42-meeting.test.ts)

## 背景

- 例会链路的收尾纪要以 `::: minutes` 容器承载三栏（决议 / 待办 / 风险），待办行格式为 `- 待办 | @负责人 事项`——@ 是**派活锚点**（用户点击后回填 `@负责人 ` 草稿再自行发送，ADR 0064 / ADR 0115），不是对成员的即时应答；
- 但引擎的 `parseMentions` 对成员提及的既有口径是「正文任意位置的 `@成员名` 即召唤」（仅「交还用户」要求行首 `@用户`，ADR 0004）——待办行因此被解析为对本轮发言者的转交，owner 被重新入队，波次外扩（brainstorm 例会实测 5 波 → 8 波，eval `turns_lte 5` 失败）；
- 这不是 mock 专属问题：真实模型按协议输出同构待办时会触发同一误判；而「把 @ 从纪要里去掉」则违反 RT-4 的展示契约（待办必须带负责人锚点）。

## 决策

1. `parseMentions` 在解析**成员提及**（转交）与**「交还用户」判定**前，先剥离正文中的 `::: minutes` 容器块（`stripMinutesBlocks`）——块内 `@成员名` 不进入 `mentions`，块内 `@用户` 不构成交还；
2. 剥离采用**栈式深度匹配**：开标记行 `^:::(?!:)\s*([a-zA-Z][\w-]*)\s*(.*)$` 与闭标记行 `^:::\s*$`（与 remark-ext 容器语法的同一正则口径，行首空白耐受、防 `::::`）；遇到未闭合的 `minutes` 容器时**整体不剥离**（fail-safe，宁可保守放过）；
3. 仅豁免 `minutes` 容器；其余容器（`meeting` / `pan` / `verdict` 等）内文本仍按常规解析；解析结果返回的 `text` 仍为**原文**（容器渲染 / 消息存档不受影响，仅内部判定使用剥离后文本）；
4. 协议层同步约定：纪要待办 @ 是派活锚点、不构成转交，收尾发言需**另行单独一行**给出转交（议毕即 `@用户` 交还）——协议与解析层两头对齐，互为兜底。

## 理由

- **语义单一事实来源放引擎**：@负责人 的「派活」与「转交」歧义属于系统级语义，若只在 mock 侧改写（或只靠协议叮嘱）则对真实模型无保障——解析层豁免对 mock 与真实链路同时生效，且不牺牲展示格式；
- **与既有容器纪律同源**：M37 起容器（pan / verdict / checklist）就是「自描述结构化区域」；本轮把「结构化区域内的 @ 不具有边信道语义」显式化为解析规则，与 ADR 0034 的容器语汇一致；
- **fail-safe 保守**：未闭合容器不剥离（按普通文本处理）——宁可退回旧行为（@ 可能被误判为转交），也不误吞真实转交指令；栈式匹配保证嵌套 / 连续容器场景的正确边界；
- **改动面最小**：只在 `parseMentions` 入口做一次文本预处理（其余解析与引擎管线零改动），`text` 返回原文使下游渲染 / 存档零感知；
- **可测试**：`stripMinutesBlocks` 为导出纯函数，单测锁定（块内 @ 豁免 / 块外 @ 照常 / 未闭合不剥离 / 嵌套与连续块边界）；例会链路测（`m42-meeting.test.ts`）与 eval 13 端到端锁定波次数。

## 被否决的方案

- **改 mock 纪要待办格式（去掉 @ 或换写法）**：违反 RT-4 契约与协议展示格式，且只对 mock 生效——真实模型输出同构文本时误判依旧；
- **只靠协议叮嘱模型「待办 @ 不算转交」**：提示词约束不可靠（真实链路无强保证），且解析层若仍按其为转交，波次外扩的后果（入队 / 循环检测 / 回合上限）依旧；本批仍同步更新了协议，但作为**理由说明与双保险**而非唯一手段；
- **把成员提及改为「仅行首 @ 才召唤」**：会破坏既有提及语义（行内 @ 召唤是 M8 起的产品行为与测试基线），影响面远大于本问题；
- **在 minutes 块内「检测到 @ 就跳过该行」而非剥离整块**：行级跳过无法覆盖多行待办 / 嵌套容器 / 后续行内 @用户 等边界，且与 remark-ext 的块级解析口径分裂；
- **新增消息字段标记「本次 @ 仅为派活」**：需要协议、编排、存档三侧扩字段；容器自描述（剥离）零字段成本。

## 适用与失效条件

- 适用：`stripMinutesBlocks` 与 remark-ext 的容器正则**同源**（`^:::(?!:)\s*([a-zA-Z][\w-]*)\s*(.*)$` / `^:::\s*$`）——该正则为两处联动契约，任何一处调整须同步另一处并复核测试；
- 失效条件：minutes 容器语法升级（嵌套 minutes / 新闭标记 / 引号内伪容器）须复核栈式匹配；若未来把「派活」升级为直发语义（ADR 0064 被推翻），则本豁免须重审（届时块内 @ 应再度参与转交解析或改走显式工具）；若新增其它「块内 @ 非转交」的容器（如新的任务派发容器），应复用同一剥离机制而非新增特判。
