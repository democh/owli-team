# ADR 0089：工具运行时惰性 participants（Lazy Participants Getter in Tool Runtime for Same-Turn Invite-then-Handoff）

- 状态：Accepted
- 引入：M46
- 相关：[design.md §54](../design.md)、ADR 30（会话动态成员）、ADR 48 / 49（计划审批 / 计划派发与任务面板）、ADR 60（会话级定时任务）、ADR 86（召集单一收口）

## 背景

- `ToolRuntime.participants` 原为「回合开始快照」（engine.ts `buildToolRuntime` 组装时一次性读取编制表）；
- 调度官的自然工作流是**同一回合**「先 `invite_members` 召集、再 `handoff` 派发」；快照不含刚召集的新成员 → handoff 误报「不在场」；
- 候选：① 快照改**惰性 getter**（每次访问读实时成员表）；② 要求模型跨回合完成（本回合召集、下回合派发）；
- 同类缺陷面：plan owner 校验（计划步骤负责人刚被召集）与 schedule target 校验（定时任务目标刚被召集）读的是同一快照——三处同类。

## 决策

1. `ToolRuntime.participants` 改**惰性 getter**（`buildToolRuntime` 内 `get participants()`）：每次访问读 `sessions.getSession().participantIds` 实时映射（id + 名）；
2. 同源受益三处：handoff 目标校验、计划步骤 owner 校验、定时任务 target 校验——同一回合内新成员即时可见；
3. mock 剧本与真实模型走同路径（同回合「召集 → 派发」闭环）；e2e 全链验证（召集事件条出现后同波派发）；
4. 类型面保持 `Array<{id, name}>` 不变（读取方零改动）。

## 理由

- **同回合闭环**：真实模型天然倾向「一个回合内完成召集 + 派发」（少一次模型往返）；「要求跨回合」是脆弱协议——模型不遵守即失败，且失败态（召而不派）无法从协议层修复；
- **读放大可控**：成员表为内存读取（`participantIds` 数组 → `prompts.get` 映射，O(n)，n = 会话成员数量级 10）；每回合工具调用次数有限，累积成本可忽略；
- **顺带修正三处同类缺陷**：原先「同回合召集 → 派发到新成员 / 计划点名新成员 / 定时任务指向新成员」全部会误报——一处修复三处受益；
- **架构一致性**：波末 `decideHandoff` 本就读实时成员表（活引用）——工具运行时此前是唯一的「快照例外」，修复后全链统一为「实时成员表」单源。

## 被否决的方案

- **跨回合协议**（回合 1 召集 / 回合 2 派发）：依赖模型遵守回合纪律；mock 剧本需双回合编排、eval 断言复杂化；且「回合 2」可能因循环检测 / 用户插话改变波次结构；
- **快照 + 召集后手动刷新局部变量**：工具间状态传递脆弱——谁刷新 / 何时刷新无单一所有者，等价于把一致性责任推给每个工具实现；
- **每次工具调用重建整个 runtime**：组装成本（配置 / 缓存 / 连接等引用传递）远大于惰性读取的单次映射成本。

## 适用与失效条件

- 适用：成员表为权威实时源（`setParticipants` 就地修改 + 广播，ADR 30 / 91）；会话成员数量级为十位；
- 失效条件：
  - **成员表改为异步一致模型**（多副本 / 缓存层 / 分布式）——惰性读取需补一致性语义（读己之写保证）；
  - **超大会话**（百人级成员）——需评估每回合多次读取的累积成本（可加回合级 memo，但需保证召集后失效——与惰性语义冲突，届时单独评审）。
