# ADR 0117：PK 只做显式结构化触发——四容器族与「已响应」配对推导（M43）

- 状态：Accepted
- 引入：M43
- 相关：[design.md §72.1 / §72.2](../design.md)、[docs/scene-chat-design.md §11](../scene-chat-design.md)、ADR 0112（场景工作区体系：arena 形态与结构键契约）、ADR 0034（Markdown 容器语法与包体纪律）、ADR 0064（交互卡片回填 = 草稿）、ADR 0118（对决布局）、ADR 0119（裁决回填）、[client/src/lib/pk.ts](../../client/src/lib/pk.ts)、[client/src/components/chat/md-ext/](../../client/src/components/chat/md-ext/)、[agents/debate/_protocol.md](../../agents/debate/_protocol.md)、[agents/brainstorm/_protocol.md](../../agents/brainstorm/_protocol.md)、[agents/negotiation/_protocol.md](../../agents/negotiation/_protocol.md)

## 背景

- §11（PK-1..PK-5）规划了多方 PK 范式（对决组 / 缺陷-修补配对 / 判定卡 / 裁决卡 / 计分板）——彼时以 ADR 0075 / 0076 / 0077 预定号规划（该区间已被后续批次占用，编号让位后决策并入本 ADR 族）；
- M52-A（ADR 0112）已交付 arena 形态（席位卡 + 回合轴 + 计分标题），但「对抗」的语义（谁和谁对决 / 缺陷是否被修补 / 结论如何裁决）无内容层承载；评审范式（M24）已有 ReviewRecord 结构化判定，无渲染承载（常规「评审」徽章）；
- 触发口径的关键约束：对抗是「对话过程」的语义，若用启发式（如 mentions 交替 A→B→A 判定对抗）推断，误判会渲染错乱（普通讨论被拆成二栏 / 无对决也挂裁决卡）；而漏判仅少一层呈现增强——两者成本不对称。

## 决策

1. **PK 只做显式结构化触发，不做启发式检测**：三个显式入口——① 评审范式产物 ReviewRecord（mode=review + 判定记录，PK-3）；② 协议容器 `::: debate <题面>`（对决显式声明，PK-1 容器入口）；③ 结构化容器 `::: claim` / `::: findings` / `::: offer`（主张 / 缺陷 / 报价，PK-2 与面板数据源）；mentions 交替启发式未来仅可作为提示条，不驱动布局判定；
2. **四容器族语法与卡片**（remark-ext builder + React 卡片 + fail-safe 降级，ADR 0034 同口径）：`::: claim <主张>`（`细节：…` 要点行 + 条目 `- 论据 | 证据`）→ ClaimCard 分层折叠树；`::: findings <标题>`（条目 `- 缺陷 N | 描述 | 修补方向`）→ FindingsCard 配对卡；`::: offer <主题>`（字段行 `- 键：值` + 条目 `- 项 | 内容`）→ OfferCard 报价卡；`::: debate <题面>`（双方立场行）→ DebateCard 题面卡。条目统一转 `data-items` JSON，卡片与 `lib/pk.ts` 纯函数同源解析；未闭合容器无卡片壳、解析失败 raw 静态兜底；
3. **「已响应」配对推导在前端按提及扫描**：`findingMentions`（正文「缺陷 N」编号扫描，排除 `- 缺陷 N |` 定义行自身）× `respondedSig`（消息 id → 其后同会话消息的提及编号集合签名，按消息粒度订阅）；findings 行命中 → `data-responded` + 「已响应」徽章 + 头部「N/M 已响应」计数；尾条 / 无场景 ctx 不标（未完结不判）；配对推导不落库、不走服务端接口（数据已在前端消息流，ADR 0112 约束同口径）。

## 理由

- **误判成本不对称**：对抗布局是对消息流的拆分呈现（二栏 / 裁决卡 / 计分板），启发式误判会让普通讨论「看起来像在吵」并挂出不存在的裁决入口；漏判只损失增强层（消息照常渲染）。宁缺毋滥——与 ADR 0077 规划的原始口径一致；
- **容器是「本次对抗」的自描述范围声明**：`::: debate` / `::: findings` 出现即声明对抗语境，与 roundtable 的 `::: meeting`（ADR 0115）同构——无需会话开关、无需引擎状态位，任意场景可输出；
- **逐字编号使配对可核**：`- 缺陷 N | 描述 | 修补方向` 的编号在本对局内稳定（协议纪律），响应方复用「缺陷 N」编号——提及扫描按编号精确匹配，比语义相似度 / 时间窗推导更稳且可测（纯函数单测锁定）；
- **前端推导零接口成本**：消息流已在前端（`useSceneMessages`），配对仅是纯函数投影；落库需要协议、编排、存档三侧扩字段，收益为零（与 ADR 0112 / 0115 的「形态层纯前端派生」约束一致）；
- **评审入口复用既有语义**：ReviewRecord 是 M24 已落库的结构化产物（verdict / findings / target），PK-3 只是渲染承载（runId + agentId 匹配）——不新增数据链路，未命中回退常规徽章（零回归）。

## 被否决的方案

- **mentions 交替启发式检测对抗**（A→B→A 判定对决）：误判渲染错乱成本远高于漏判；普通讨论 / 头脑风暴中的交叉回应极易触发；启发式无法界定「对决范围」（哪几条消息属于本对决）；
- **宽松时间窗配对「缺陷 → 修补」**：不要求编号复用的时间窗推导会大量误配（把无关发言计入已响应）——计分板与配对卡的数据失真比不展示更糟；
- **服务端推导配对并落库**：需要协议 / 编排 / 存档三侧扩字段与迁移；数据已在前端且推导为纯函数（可单测），服务端收益为零；
- **约定「所有容器内编号都是配对锚点」**：编号语义（缺陷编号 / 论点编号 / 报价编号）在容器间不同构，扩大到全容器会跨语义误配；仅 findings 编号参与配对；
- **无编号也按语义相似度点亮「已响应」**：不可测且不可核（用户无法验证为何点亮）；宁缺毋滥。

## 适用与失效条件

- 适用：四容器（claim / findings / offer / debate）为全局能力（任意场景可输出）；`lib/pk.ts` 的解析 / 配对 / 推导纯函数与四卡及 ArenaStage 面板（论断树 / 报价流）共用同一数据源；协议三侧（debate / brainstorm / negotiation）的容器纪律是本推导的语义前提；
- 失效条件：容器语法升级（嵌套 / 新字段行 / 编号格式变化）须三侧（remark-ext / 卡片 / lib 纯函数）同步复核；「缺陷 N」编号口径若被协议调整为其它格式（如 #N / 序号列表），`findingMentions` 须联动；若未来引入启发式提示条，须遵守「提示不驱动布局」的边界；DUEL_STANCE 与 `::: debate` 触发解耦（前者属 ADR 0118 分侧口径），分侧表调整不改变本决策。
