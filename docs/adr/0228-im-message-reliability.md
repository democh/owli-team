# ADR 0228：IM 消息接收可靠性（幂等提交 · 本地待发箱 · 代际对账 · 真实阅读水位）

- 状态：Accepted
- 引入：M90
- 相关：[ADR 0134](0134-multi-user-foundation.md)（多用户基座）、[ADR 0188](0188-user-topic-and-inbox.md)（用户主题与收件箱）、[ADR 0189](0189-server-authoritative-unread.md)（服务端权威未读）、[ADR 0192](0192-friend-graph-and-privacy.md)（好友与隐私）、[ADR 0198](0198-blocked-dm-message-semantics.md)（拉黑消息面）

## 背景

M79/M80 已把私聊、群聊、好友、未读、已读回执与实时通知接入同一个会话模型。专业 IM 的下一层要求不是再加界面入口，而是**让已发出的消息不重复、不丢失、不误判为已读**。代码核实的四个缺口：

1. **发送非幂等**：`POST /sessions/:id/messages` 无客户端提交标识；服务端落库成功但响应在途丢失时，用户重试会再写一条，并可能再起一次 AI Run。
2. **失败语义错误**：消息落库后引擎启动失败会整体返回 `400`；客户端把「消息未发送」回退，用户重试造成重复发言。网络失败时正文只留在输入框，刷新即丢。
3. **补偿不完整**：通知序号是进程内计数器，重启后从 1 开始；客户端保留旧游标并丢弃更小 `seq`，只能等下一次列表刷新。收件箱接口返回「这一页」的条目却给出全局最大游标，积压超过一页会跳过中间条目。
4. **已读不等于看到**：已读上报取当前已加载消息的最大 `seq`，而首载只加载最近 100 条、虚拟列表还有 overscan；用户上滑阅读历史时，新消息也会被标为已读。

## 决策

1. **幂等提交（服务端权威）**
   - 发送体新增可选 `clientMessageId`（`[A-Za-z0-9_-]{1,100}`）；同一会话 + 作者 + 标识唯一。
   - 新增 `message_submissions`（迁移 v38）保存请求摘要、消息 id 与运行结果；消息主表、接收凭据、会话消息序号在**同一事务**写入，唯一约束冲突即回滚，内存缓存不落地半条消息。
   - 相同标识 + 相同摘要 → 返回原消息（`deduplicated: true`）；摘要不同 → `409`；消息已接收但随后被删除 → `410`，重试不复活内容。
   - 会话新增持久化 `message_seq` 水位：删除末条后重启也不复用序号，避免已读游标把新消息误判为旧消息。
2. **本地待发箱替代「失败回退输入框」**
   - 客户端按账号持久化 `ma:outbox:<owner>:<clientMessageId>`；每条包含内容、范式、附件、目标会话与状态（queued / sending / failed）。
   - 同会话单车道保序：前一条未确认时后一条不越过；不同会话可并行。
   - 请求超时 20s；失败保留原条目并在气泡上方原位「重试 / 移出待发箱」，重试复用同一 `clientMessageId`。
   - 刷新或崩溃后恢复：`sending` 一律降级为「发送结果待确认」，**不自动重发**，避免自动二次唤起 AI；用户点击重试后由服务端幂等判定是否已接收。
   - `notify:turn-end` 或 HTTP 响应任一先到即确认并清除磁盘条目；确认后不再因为 HTTP 后续失败恢复为失败态。
   - 存储不可用（配额 / 隐私模式）时不发请求、不清输入。
3. **消息接收与 AI 派发解耦**
   - 引擎启动失败 → `201 { message, dispatchError }`；消息视为已发送，客户端提示「消息已发送，AI 未完成启动」。
   - 已接收消息的运行结果（`runId` / `injected` / `queued`）记入接收凭据；重放直接返回同一结果，不重复调用引擎。
4. **通知代际与缺口的显式对账**
   - `NotifyHub` 生成进程级 `epoch`，随 `welcome`、通知帧与轮询响应下发；客户端发现代际变化即清空游标、重新订阅，并做一次 REST 权威对账（收件箱 + 会话列表 + 当前会话消息）。
   - 订阅时游标超出当前缓冲上界或早于缓冲下界 → 服务端直接发 `resync(replay-gap)`；轮询结果 `truncated` 同样触发对账。
   - 收件箱改为 `nextCursor + hasMore`（每页多取一条判断是否还有），游标只推进到**实际收到**的最后一条；新增 `inbox_cursors`（v38）让清理已读通知不回退同步水位；客户端循环拉取至末页。
   - 对账快照若在请求期间被新帧超越则丢弃重试（有限次），不覆盖更新状态。
5. **已读跟随真实阅读位置**
   - 已读水位取消息真实 DOM 与滚动容器视口的交集：预渲染 overscan、视口外消息、未读到末尾的长消息与流式消息都不计入。
   - 仅在页面可见且窗口有焦点时上报；窗口恢复焦点、滚动、尺寸变化与节点增减都会重新评估。
   - 上报走 REST 并等待 `lastReadSeq` 确认；失败保留待重试（4xx 确定性失败丢弃，5xx/网络退避重试）。服务端把水位夹到会话最大 `seq`，并拒绝非法值。
   - 读到本地最新一条后清会话徽章；剩余未读仍以服务端聚合为准，不在导航或加载时提前清零。

## 理由

- **幂等键放在服务端唯一约束上**：客户端可以伪造/重放请求，只有数据库约束能保证「一次提交一条消息」；同时把凭据与消息同事务写入，避免「消息在、凭据丢」导致重试重复。
- **待发箱放本地而非服务端**：待发消息属于某台设备的输入意图（附件路径、草稿状态）；服务端只需承接已提交请求。localStorage 与既有草稿同层，跨账号按前缀隔离。
- **崩溃后不自动重发**：自动重放会在「服务端已接收但结果未知」时重复触发 AI 运行，成本与上下文污染远高于一次手动确认。
- **epoch 而非持久序号**：把内存重放缓冲的序号升级为持久化序列是更大的改造；代际只用于识别「序号不可比」，用一次权威对账兜底，和既有 REST 降级路径同构。
- **阅读位置取 DOM 而非加载状态**：加载量与阅读量在多端、虚拟列表与分页下不等价；DOM 交集是唯一不会被预取放大的信号。

## 被否决的方案

- **所有接口统一 `Idempotency-Key` 中间件**：本批只有「消息 + 触发运行」存在重复副作用；全局中间件要新增表与清理策略，收益不匹配。
- **服务端待发箱表**：需要设备标识、附件临时态与跨设备冲突合并，等于重建投递层；当前客户端缓存 + 幂等提交已覆盖断网与刷新。
- **失败时把正文塞回输入框**：会与用户新输入竞争，且丢失附件与顺序语义；待发箱保证「已提交的内容仍在队列里」。
- **重连时依赖 `since` 单游标全量重放**：进程重启后序号不可比；且重放缓冲只有 200 条，超出仍要 REST 兜底。
- **打开会话即清零未读**：导航不等于阅读；会吞掉用户未看到的新消息，与「已读跟随视口」自相矛盾。
- **WS `read` 帧作为唯一通道**：断线时静默丢弃，且无法确认落库；改为 REST 确认，WS 帧保留给旧客户端。

## 适用与失效条件

- 适用：单进程 Node/SQLite 部署（含 `NOTIFY_BUS=db` 多实例快路径）；单用户兼容模式与多用户模式并存。
- 失效条件：
  - 引入真正的离线推送 / 多设备同步中心时，待发箱需要升级为服务端投递队列（设备维度、冲突合并、附件暂存）；
  - 若把消息存储迁移到 PostgreSQL 多主写入，`message_seq` 需改为按会话的序列或分布式序号，并重新评估事务边界；
  - 若引入端到端加密，接收凭据中的请求摘要不能再保存明文内容哈希（需改为密文摘要或不存摘要），`409` 判定口径需重写；
  - 若产品允许「已发送消息自动重放到 AI」，本 ADR 第 2 条的「不自动重发」需要重新评审成本与幂等边界。
