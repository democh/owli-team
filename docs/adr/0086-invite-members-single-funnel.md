# ADR 0086：召集单一收口（Invite Funnel: Dispatcher-Only `invite_members` Sharing the Members-API Kernel）

- 状态：Accepted
- 引入：M46
- 相关：[design.md §54](../design.md)、ADR 30（会话动态成员：members API + system 消息）、ADR 50（资产控制台：引用检查）、ADR 82（调度官为显式一等成员）、ADR 87（roster_catalog 注入）

## 背景

- 「把不在场角色拉进会话」需要确定唯一入口：候选方案 ① 调度官专属工具 `invite_members`；② 全体成员可召集（任意角色可拉人）；③ 新开会话级召集 API 端点；
- 约束：**权限最小**（召集 = 改会话成员表的强动作）；**语义不漂移**（用户手动邀请已走 `POST /sessions/:id/members`，工具通道不能另起一套校验 / 排序 / 广播）；**审计一致**（两入口的事件条 / trace 形态必须一致）。

## 决策

1. `server/src/tools/roster.ts` 新增 `invite_members` 工具（`tier: 'core'`，非只读）：参数 `agent_ids`（≤20）/ `scene_id`（整链召集场景默认编制）/ `reason`（写入事件条与 trace 的一句话理由）；
2. **按工具白名单实现权限**：仅调度官 `AGENT.md` 的 `tools:` 显式声明该工具，其他角色一律不可见——权限即白名单，无运行时角色判断；
3. **共享内核 `inviteMembersCore`**：与成员 API 抽出同一实现（成员校验 / 编制链排序 / 事件条 / `notify:members-changed` 广播 / trace）——路由与工具双入口行为逐字一致，仅措辞区分（用户「邀请了」/ 调度官「召集了」）；
4. 幂等与上限：已在场成员自动跳过（回执 `already` 列表，不报错）；单次解析后 ≤`INVITE_MAX_MEMBERS`（20，对齐成员 API 上限），超出错误回灌引导分批；
5. 成员需增援 → `handoff` 回调度官发起（成员自身无召集权，见 ADR 85 的「单一收口」原则）；
6. 范式只读门控自动隐藏：`invite_members` 非只读 → plan / review 回合不进工具清单（既有 `forAgent(agent, mode)` 门控，零新增代码）。

## 理由

- **权限最小**：「改成员表」这一强动作只对调度官开放；相比「运行时判断当前角色是否允许召集」，白名单可见性是更强的静态约束（工具不出现在清单 = 模型不可能调用）；
- **单源防漂移**：校验 / 排序 / 事件条 / 广播四处若双实现必然漂移（历史教训：事件条措辞与成员排序在双通道场景反复对齐）；共享内核让 API 与工具入口同源同测；
- **可审计**：召集落 system 事件条 + trace `dispatch:invited {agentIds, sceneId?, reason}`——与用户手动邀请同一可回放形态；
- **幂等安全**：重复召集不报错不重复拉人（回执引导直接 handoff），契合模型可能的重复调用行为。

## 被否决的方案

- **全体成员可召集**：权限扩散——任意成员可无限拉人，会话编制失控；且与「调度是编排原语」的定位冲突（业务成员不应改变会话结构）；
- **新开召集 HTTP 端点**：与工具通道双实现必然漂移；成员 API 的校验语义内核已可复用，新端点纯冗余；
- **运行时角色判断**（工具对所有人可见、执行时拒绝非调度官）：无效工具位占满所有角色的工具清单（上下文成本），且模型反复试错消耗回合；
- **`list_agents` 检索工具 + 召集二段式**：见 ADR 87（目录预注入已覆盖发现面）。

## 适用与失效条件

- 适用：当前「用户 + 调度官」双入口模型；v1 召集为单方动作（无需被召集方确认）；
- 失效条件：
  - **多人自治形态**（成员直接拉人 / 小队自治）——权限模型需重估（可改为「成员提议、调度官执行」的审批形态）；
  - **召集需要被召集方确认**（审批式入会）——工具体验需引入挂起语义，与 ADR 91 的事件形态同步扩展。
