# ADR 0045：外部技能适配规范——来源选择、改写原则与预载绑定

- 状态：Accepted
- 引入：M23
- 相关：[design.md §37](../design.md)、agents/README.md「技能库与预载」

## 背景

- 诉求：为全部 34 个角色从外部生态引入「好用的技能」（官方 create-skill / pptx 等 + 社区职能库），且必须贴合每个角色的职责定义，并能在本仓真实工具面内执行。
- 本仓技能机制约束（M19 起）：单文件 `skills/<name>/SKILL.md`（front-matter 三字段）、mtime 热更新、`<available_skills>` 索引常驻 + 预载正文进系统提示 L3（可裁剪层）、`load_skill` 按需加载。
- 工具面约束：无 Python / 无二进制产出能力；`run_command` 默认关闭且白名单；多数角色无浏览器与 `calc`。
- 外部生态事实：多数技能依赖 `scripts/`（Python / node）或产出二进制（pptx / docx / xlsx / pdf）；社区技能存在 prompt injection 与供应链风险（Snyk ToxicSkills 调查记录），不能原样引入。

## 决策

1. **只引方法论，不引代码**：外部技能一律改写为本仓可执行的单文件中文方法论（触发条件 + 可执行步骤 + 检查清单 + 真实工具用法 + 交付约定）；禁止携带 `scripts/`、外部依赖或网络下载步骤。
2. **工具面一致性**：技能只引用本仓真实工具与 Markdown 容器（`::: kpi / timeline / mail / option / cols / details`、`chart` / `mermaid`）；预载角色缺某工具时用「如可用」降级并给替代路径（全库 13 个文件打过该补丁）。
3. **产出形态映射**：无二进制产出能力 → pptx → HTML 演示稿（`deck-authoring`）、xlsx → CSV + 分析报告（`spreadsheet-modeling`）、docx → Markdown 正式文档（`formal-document`）；无法映射的整技能弃用（pdf：无解析能力）。
4. **来源多元化**：官方（文档 / 开发工艺）+ 社区职能库（销售 / HR / 客服等业务向）+ 通用设计规范（Vercel 界面指南 / AccessLint / Bencium）；来源清单登记于 design §37。
5. **预载绑定策略**：34 角色全部显式配置 `skills:`（1–4 个/角色，上限 4）；组 `_group.yaml defaultSkills` 仅作兜底；每个技能至少被一个角色预载，其余按需加载。
6. **验证闭环**：`check:skills`（front-matter / 目录一致）+ 34 角色引用交叉校验；受影响测试断言同步（`tests/m21.test.ts`）；上下文预算随系统层扩容同步（`tests/context.test.ts` 夹具 6k → 10k）。

## 理由

- 原样引入 scripts 型技能在本环境不可执行，会造成「技能说能做、工具做不到」的信任崩塌；方法论改写保证「读完就能干」。
- 「如可用」兜底优于按角色拆技能文本：一份技能服务多个角色（预载 + 按需），兜底保证任何角色加载后都有可执行路径。
- 显式绑定优于依赖 `defaultSkills`：M23 前 24/34 角色无技能直达且营销组全靠兜底；显式化后每个角色的技能是其职责的可审计声明（检查脚本与测试可验证）。
- 来源多元化避免职能缺口：官方覆盖文档与开发工艺，社区补业务职能，UI 源补设计工艺；单一来源必然留下盲区。

## 被否决的方案

- **原样复制外部技能（含 scripts）**：本环境不可执行；且社区技能存在注入与供应链风险。
- **只引官方 anthropics/skills**：职能覆盖不足（销售 / HR / 税务 / 供应链等业务向缺失）。
- **为每个角色现写专属技能（不复用）**：38 技能中多数服务 2+ 角色（deep-research 服务 4 角色），逐角色重复会放大维护成本并造成口径分叉。
- **技能正文内联全部规则（不做步骤 / 清单化）**：太长且不可操作；本仓统一「步骤 + 清单 + 模板 + 输出约定」结构。
- **pdf 技能用 read_file 硬凑**：误导性强（说得出做不到），弃用并在文档说明原因。

## 适用与失效条件

- 适用：任何外部技能进入本仓（含未来新增）必须按本 ADR 改写与登记；预载上限 4；新增技能必须通过 `check:skills` 且覆盖引用角色的工具白名单（或「如可用」兜底）。
- 失效条件：工具面发生质变（引入 Python 沙箱 / 二进制产出通道 / 默认开启的受限 `run_command`）时，可放宽「改写为方法论」原则，按新能力重新评估来源技能的可执行性。
