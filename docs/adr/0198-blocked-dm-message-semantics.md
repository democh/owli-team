# ADR 0198：拉黑后的消息面语义——不可联系与协作面隔离（M79-H）

- 状态：Accepted
- 引入：M79-H（2026-09-20）
- 相关：[server/src/routes/sessions.ts](../../server/src/routes/sessions.ts)、[server/src/store/friends.ts](../../server/src/store/friends.ts)、[server/tests/m79-chats.test.ts](../../server/tests/m79-chats.test.ts)、[docs/social-collab-design.md](../social-collab-design.md)

## 背景

- ADR 0192 定义拉黑四面切断 = **订阅 / 搜索 / 请求 / 私聊创建**；实现复核发现：双方既存的私聊会话仍可互发消息——拉黑后对方仍有可达的骚扰通道，与用户对「拉黑 = 不可联系」的直觉预期不符；
- 设计 §21 风险表将「拉黑即时生效」列为骚扰兜底，但未定义既存会话的消息面；M79-H 审计确认此为语义缺口（非实现缺陷）。

## 决策

1. **发送侧拦截**：拉黑对（任一方向为 `blocked`）在 `kind='direct'` 会话 `POST /sessions/:id/messages` → **403 拒发**（落库前拦截，附件校验之前；不产生消息、通知与未读）；
2. **文案按视角区分**（不泄漏拉黑事实——与建 DM 的 400 文案同族）：拉黑方本人「你已拉黑对方：解除后可继续聊天」（可操作指引）；被拉黑方「对方设置了隐私限制，无法发送消息」（中性）；
3. **历史可见**：既有私聊历史不回删、不撤销订阅（仍可回看上下文）；**编辑 / 删除既有消息不受限**（非联系行为，且属数据管理权）；
4. **协作面隔离**：拉黑仅作用于社交面——共享团队会话（team）内的消息与协作一律不受影响（owner 通过共享机制管理参与者，拉黑不构成协作面的撤销语义）；
5. **单点实现**：`routes/sessions.ts` POST /messages 前置 gate（`deps.friends` 缺省时零影响——兼容单用户模式与精简测试环境）；解除拉黑即时恢复。

## 被否决的方案

- **双向统一中性文案**：拉黑方本人收到「对方设置了隐私限制」会困惑且无解除指引；分视角文案的信息增量仅对拉黑方本人（已知事实），无泄漏代价；
- **静默丢弃（接收方过滤）**：发送方无感知（以为已送达）、消息落库污染历史与未读预算，且给接收方留下垃圾内容；
- **撤销 DM 主题订阅**（设计 §9 撤销矩阵字面扩展）：发送已被拦截，撤销只会让历史不可回看，收益为负；
- **团队会话同拦**：把社交隐私语义强加于协作面——群里无法与拉黑对象协作违背团队会话的初衷，也把「拉黑」变成工作攻击手段。

## 边界与后续

- 解除拉黑（`unblock`）即恢复发送，无需数据修复；
- 群聊内与拉黑对象的互动不受限（同上协作面隔离理由）；
- 多实例/总线演进不改变本语义（gate 在写路径单点）。
