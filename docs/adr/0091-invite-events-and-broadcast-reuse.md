# ADR 0091：事件与广播复用（Invite Events Reuse System Messages, `notify:members-changed`, and Trace）

- 状态：Accepted
- 引入：M46
- 相关：[design.md §54](../design.md)、ADR 11（异步通知通道：SSE + WS 双通道）、ADR 30（会话动态成员：members API + system 消息）、ADR 86（召集单一收口）

## 背景

- 召集动作需要三件事同时成立：**实时可见**（成员面板 / 协作图谱 / 事件条即时更新）、**可回放审计**（重开会话后召集史仍可见）、**可观测**（诊断 / eval 可断言）；
- 候选方案：① 复用 system 事件条 + `notify:members-changed` + trace `dispatch:invited`；② 新增专用 SSE 事件类型（如 `roster:invited`）；
- 约束：前端零改动优先（成员变更处理链在 M16 已就绪）；召集动作的措辞与用户手动邀请保持可区分（审计可辨来源）。

## 决策

1. **事件条**：`{调度官名} 召集了 {名单} 加入协作（{reason}）`——普通 system 消息（持久化、可回放；`SystemMessage` 直接渲染文本，无解析依赖）；
2. **广播**：复用 `notify:members-changed`（M16 成员 API 既有载荷 `{session, message}`）——客户端 `ws-store` 既有处理链直接生效（成员面板 / 事件条 / 图谱零新订阅）；
3. **trace**：`dispatch:invited {agentIds, sceneId?, reason}`（观测面：诊断与 eval 断言锚点）；
4. **措辞区分**：用户手动邀请「邀请了」/ 调度官「召集了」——经 `inviteMembersCore` 的 verb 参数单源控制（ADR 86）。

## 理由

- **三通道各司其职**：事件条管「人看」（消息流内的审计痕迹）、广播管「端看」（实时性）、trace 管「观测」（诊断 / 评测）——同一动作三种消费者，复用既有通道零新增；
- **零前端改动**：成员面板 / 事件条 / 协作图谱全部经既有 `notify:members-changed` 链路更新（M16 起就绪的处理链直接生效）；
- **持久化天然**：system 消息进消息表——重开会话可见完整召集史（对比瞬时 SSE 事件需另建回放机制）；
- **fail-safe 渲染**：事件条为纯文本（无结构化解析），摘要压缩 / 导出 / 搜索（FTS）零特判。

## 被否决的方案

- **新增 SSE 事件类型**：双通道分叉——SSE 管实时 / system 条管回放，客户端需新增订阅与归约逻辑，且回放态（重新加载后）缺失（SSE 瞬时事件无历史）；
- **静默召集**（仅 trace）：用户不可见——违背「可见可审计」原则（ADR 82），成员面板突然多人的体验事故；
- **富交互召集**（审批流 / 卡片确认）：超出 v1 范围（见失效条件）；
- **专用 WS 主题**（如 `__roster__`）：与 M16 成员变更语义完全重叠，双主题必然出现「同一变更两条广播」的幂等噩梦。

## 适用与失效条件

- 适用：v1 召集为「单方动作 + 文本可表达」形态；成员变更处理链稳定（ADR 30）；
- 失效条件：
  - **召集需要用户确认**（审批式召集）——需接入 M7 审批通道，事件形态扩展为挂起卡；
  - **召集需要富交互**（如被召集方接受 / 拒绝、召集卡选择）——需引入交互消息（M37 容器族 / 审批卡先例），`notify:members-changed` 载荷可保持不变；
  - **多调度官**——事件条措辞需含来源标识（当前措辞以调度官名为准，天然可辨）。
