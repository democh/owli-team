# ADR 0058：专业级附件体系与多模态通道（Attachments & Multimodal Pipeline）

- 状态：Accepted
- 引入：M33
- 相关：[design.md §48](../design.md)、design.md §21（工具系统与 Harness）、ADR 1（服务端 LLM 代理）、ADR 10（消息双形态）、ADR 14（工作区沙箱）、ADR 19（上下文工程：五层装配 + 压缩）、ADR 46（交付件多格式预览）、ADR 55（编码代理能力基线）

## 背景

- M8 已建成对话上传通道（base64 直传 ≤8MB、插入 `@file:path` 文本引用）与 M24 交付件预览（docx / xlsx / pptx 服务端轻量解析），但附件在对话中的体验仍是「**文本引用 + 右侧面板**」：用户发图后模型看不到图（纯文本模型通道）、发 Office 文档后模型不知道内容（`read_file` 只按 utf8 读取，office 是二进制直接拒读）、视频 / 音频只能给路径；消息气泡里附件只是 `@file:xxx` 一行文本——**不是专业级应用的交互**。
- 用户诉求原话：「不用 Markdown 扩展，以及特殊视图场景的支持，不单单只是 chat 的方式，学习下有些的软件的交互；当前的交互需要支持文件、图片、视频、office 文档等等上传、识别以及相关的处理，做到一个专业级的应用」。拆解为四项：
  1. **不用 Markdown 扩展**：附件渲染必须是组件级原生视图（图片网格 / 视频播放器 / 文档卡），不做 `![alt](path)` 这类降级；
  2. **特殊视图场景**：消息内直显 + Lightbox 放大 + 内联播放 + 文档卡跳转预览——学习 Slack / Linear / ChatGPT 的附件交互；
  3. **上传识别处理**：图片走视觉理解（多模态 `image_url`）、Office / PDF 走内容识别（文本提取）、视频带元数据（时长 / 分辨率）；
  4. **专业级**：托盘范式（发送前预览 / 进度 / 可删）、raw 直传（大文件不膨胀）、类型白名单与安全化、持久化与回放。
- 硬约束：
  1. **零新依赖**：不引入 pdfjs / office 解析库（服务端已建成零依赖 office-preview 与 zip 读取，PDF 提取须自实现且带质量护栏）；
  2. **模型能力对齐**：LLM 通道（DeepSeek 兼容 OpenAI 协议）支持 `content: [{ type: 'text' }, { type: 'image_url' }]` 多模态数组，图片以 data URL 注入；
  3. **token 预算不失控**：视觉注入必须限量（全窗 / 单条 / 单图三级护栏），未注入的图片保留文本占位（模型可感知存在但看不见内容）；
  4. **零回归**：M8 base64 通道保留（`@file` 引用与拖拽插入不受影响）；既有 m7 / m16 / m24 测试全绿。

## 决策

1. **双通道并存，附件通道独立**：M8 `POST /sessions/:id/uploads`（base64 ≤8MB，用于「上传文件 → 插入 @file 引用」旧交互）保持不动；新增 `POST /sessions/:id/attachments`（raw 二进制 ≤200MB，无 base64 膨胀）服务附件托盘；两条通道产物同为 `uploads/` 下普通交付件（`artifact:updated` 广播，交付件面板 / Office 预览 / @file 候选全部复用）。
2. **上传协议**：raw body（`express.raw` ≤200MB，挂载在全局 4mb 之前）；文件名经 `x-file-name`（URL 编码）传递、媒体元数据经 `x-file-metadata`（JSON）可选传递（非法值静默丢弃）；签名 `safeFileName`（保留中英文、去前导点、防路径穿越、截断 120 字符）后落盘 `uploads/<ts36>-<name>`；类型白名单五类（图片 / 视频 / 音频 / Office-PDF-文本 / 压缩包），可执行与脚本类拒绝（安全边界）。
3. **服务端元数据可信化**：图片尺寸由服务端解析文件头（png / jpeg / gif / webp / bmp 零依赖探测器，覆盖客户端元数据——不可伪造）；视频时长 / 分辨率取客户端读取的媒体元数据（服务端无解码能力，标记为弱可信）；响应 `201 { attachment: MessageAttachment }`。
4. **消息携带附件**：`ChatMessage.attachments?: MessageAttachment[]`（内存 + DB `messages.attachments` 列 JSON 双写）；`sendMessageSchema` 校验 `attachments ≤10` 且 refine「content 或附件至少提供一个」（纯附件消息合法）；发送时服务端二次校验（`path` 必须 `uploads/` 前缀 + 文件真实存在，防伪造路径）；纯附件消息的会话自动命名以首个附件名兜底。
5. **多模态视觉通道**：`LlmMessageInput.content` 放宽为 `string | LlmContentPart[]`（`{ type: 'text' } | { type: 'image_url' }`）；装配器 `buildWindow` 在窗口填充后**从后往前**为最近的图片附件构建多模态内容块，三级护栏：全窗 ≤6 张 / 单条消息 ≤4 张 / 单图 ≤8MB；未注入（超配额 / 超体积 / 读取失败 / 非视觉格式如 svg）的图片保留文本占位（`[附件]` 清单块：文件名 + 尺寸 / 时长 / 体积描述，Office / PDF 附「可用 read_file 读取内容」引导）；视觉 token 按 `VISION_TOKENS_PER_IMAGE = 800` 计入窗口计量（tokenizer 与装配器同源）。
6. **文档识别管道（read_file 增强）**：新增 `util/document-extract.ts` 零依赖提取器——docx 复用 office-preview 的 OXML → HTML → 文本（标题 / 列表 / 表格）、xlsx → 工作表头 + TSV、pptx → 幻灯片大纲、pdf 自实现（zlib inflate 解压流 + BT/ET 文本算子状态机 + 字面量 / UTF-16BE hex 字符串还原 + 乱码质量护栏）；`read_file` 对 `.docx/.xlsx/.pptx/.pdf` 自动提取（≤32MB，超限引导下载），对其它二进制按类型给出可行动提示（图片提示走视觉通道、视频提示时长、压缩包建议解包后读取）。
7. **前端托盘范式**：Composer 输入框上方为附件托盘（`AttachmentTray`）——图片 / 视频显示本地 object URL 缩略图（发送前零网络预览）、文档显示类型化文件卡（图标 + 类型标签 + 体积）、上传中显示进度条、失败标红并给出原因、× 移除（上传中的项取消本地预览）；`apiUpload` 基于 XHR（`upload.onprogress` 上传进度）；发送前 `uploading` 状态拦截（不允许发送半成品附件）。
8. **消息内原生渲染（不做 Markdown 降级）**：`MessageAttachments` 组件按类型分流——图片网格（1 张大图带真实宽高比 / 2-4 张两列 / 5+ 三列 + `+N` 收尾，最多 9 张）→ 点击 Lightbox（多图 ← → 键与按钮切换、计数、Esc / 遮罩关闭）；视频封面式播放器（首帧 + 播放键 + 时长 / 分辨率角标 → 点击切换内联 controls 播放）；音频紧凑播放条；文档卡（类型图标 + 名称 + 体积）→ 点击 `requestArtifact` 打开右侧交付件面板预览（Office 服务端解析 / PDF iframe / 视频 Range 直出——复用 M24 / M30 既有能力）、右侧下载直链。附件事务与文本并存（`mb-2` 间距），Markdown 仅渲染正文。
9. **CLI 兼容层**：`textOfContent(content)` 工具（`llm/content.ts`）统一提取多模态数组的纯文本（mock provider / tokenizer / 压缩器 / 测试共用），避免多份实现漂移。

## 理由

- **双通道而非替换**：M8 通道承载「上传 → @file 引用」轻交互（适合 ≤8MB 小文件与既有引导文案），附件通道承载「托盘 → 消息内直显」重交互（大文件 raw 直传避免 base64 33% 膨胀与内存峰值）；两者落盘位置相同，交付件体系零改动复用；
- **托盘范式对齐专业软件**：上传即预览（缩略图 / 文件卡）、进度可视、失败可删、发送前可调整——这是 Slack / Linear / ChatGPT 的共同交互语言，比「上传后插一行文本」更接近专业级应用；
- **原生渲染而非 Markdown 扩展**：`![alt](path)` 无法表达视频播放、文档卡跳转、多图网格与 Lightbox；组件级渲染直接服务「特殊视图场景」，且把渲染分支与 `ArtifactKind`（交付件同口径）对齐，前后端分类逻辑单一来源；
- **视觉注入从后往前 + 三级护栏**：最近的消息最可能被追问；全窗 ≤6 保证 token 与成本可控（每图 800 token）；单条 ≤4 防止单条消息刷屏；8MB 上限防 base64 膨胀（8MB 图 → ~10.7MB data URL）超请求限制；
- **未注入仍留占位**：模型虽看不见未注入的图，但 `[附件]` 清单让它知道「用户发过图」——可主动提示用户重发或改用文字描述，优于静默丢弃；
- **零依赖文档提取**：office 三个格式复用已建成的 office-preview（M24 交付）；PDF 自实现（inflate + BT/ET 扫描）约 200 行，覆盖「文本型 PDF」主流场景（报告 / 合同 / 说明书），配乱码护栏（可打印字符占比过低时给出「疑似扫描件 / 字体编码不支持」提示而非输出垃圾）——避免为一个功能引入 pdfjs 全家桶（>1MB 依赖 + worker 复杂度）；
- **服务端元数据可信化**：图片尺寸是前端布局防跳变（aspect-ratio）与视觉护栏（超尺寸图）的依据，必须服务端探测（客户端元数据可伪造 / 可缺失）；视频时长仅为展示信息，客户端读取足够；
- **持久化到消息而非会话**：附件是「某条消息的输入」，随消息持久化（DB JSON 列）使会话重放 / fork / 导出天然携带附件，无需独立附件表与外键关系。

## 被否决的方案

- **继续用 Markdown 扩展渲染附件**（如自定义 ```image / ```video 语法块）：与用户明确诉求「不用 Markdown 扩展」冲突；且 md 扩展块在流式渲染 / 历史消息 / 引用跳转中的边界情况远多于组件级渲染；
- **单通道升级（M8 base64 通道直接放宽到 200MB）**：base64 膨胀 33% + 全内存字符串，200MB 文件在 Node 中产生 ~270MB 字符串与解码副本，内存峰值不可接受；raw 流式直传是唯一合理路径；
- **引入 pdfjs-dist / mammoth / sheetjs 做解析**：依赖体积与 worker 复杂度高；服务端已有 office-preview（M24）+ 本批 PDF 自实现，覆盖主流「文本型」文档；扫描件 OCR 属明确的能力外（提示用户而非假装能读）；
- **视频抽帧理解（首期）**：需要 ffmpeg 或 WASM 解码器（重依赖）；首期做到「封面帧（浏览器原生）+ 时长 / 分辨率元数据 + 内联播放」，抽帧理解留待后续按需评估（ADR 失效条件）；
- **@file 弹窗式文件选择器（替代托盘）**：@file 输入即引用工作区**已产出交付件**（agent 产物），与「上传新文件」是两条语义；托盘（待发附件）+ @file（引用既有文件）并存才是完整交互；
- **附件独立消息类型（`role: 'attachment'`）**：会引入消息排序 / 回合边界 / 渲染分流的全链路分支；`ChatMessage.attachments` 与正文共存（可带说明文字）更贴合「消息 = 输入 + 附件」的语义；
- **视觉注入全量（不设护栏）**：20 张图的会话每轮消耗 16k+ 视觉 token，成本与延迟不可控；且单图超 8MB 的 data URL 会超过多数模型请求体限制；
- **图片本地压缩后再上传**（前端 canvas 重采样）：会损失原始分辨率（用户可能要看细节 / 模型要读小字）；护栏在注入侧（超 8MB 不注入视觉但文件仍完整保存）而非上传侧，原始文件保真。

## 适用与失效条件

- 适用：本地单用户部署（与既有 ADR 同一产品形态）；LLM 通道支持多模态 `image_url`（当前 DeepSeek 兼容协议）；单文件 ≤200MB、单消息 ≤10 个附件的对话场景。
- 失效条件：
  - 若切换为不支持视觉输入的模型，`isVisionImage` 判定与注入逻辑需按模型能力开关（配置化），文本占位退化为唯一通道；
  - 若引入对象存储（S3 / OSS），`uploads/` 落盘路径与 `resolveSafe` 边界需重新设计（附件表 + 预签名 URL）；
  - 若需要扫描件 / 手写体识别，需接入 OCR 能力（外部服务或本地模型），document-extract 的质量护栏提示语需相应调整；
  - 若视频理解成为核心诉求（抽帧 / 字幕 / 语音转写），需新增媒体处理管道（ffmpeg / Whisper），本 ADR 的「零新依赖」前提失效；
  - 若单会话附件量级增长到需要独立附件表（配额 / 去重 / 引用计数），`messages.attachments` JSON 列方案应迁移为规范化存储。
