# ADR 0226：意图判定与自动编排（规划门 / 评审门）

- 状态：Accepted
- 引入：M88
- 相关：[ADR 0048](0048-turn-modes-and-plan-approval.md)（回合范式与计划审批）、[ADR 0049](0049-plan-dispatch-task-board.md)（计划派发）、[ADR 0223](0223-relay-control-manual-dispatch.md)（接力控制）、[ADR 0040](README.md)（平台路由 PRS）

## 背景

- M24 把「规划 / 执行 / 评审」做成了三个并列的用户选项（Composer 三 chip + 会话 `planFirst`），要求用户在**发消息之前**判断这一条该不该先出计划。实际使用中这个判断应该由系统完成：用户关心的是"把事办对"，不是"选哪个模式"。
- 更关键的是：PRS（平台路由步）**已经**在做范式判定（`assignments[].mode` + 系统提示词规则），但结果被降级成一句便条文字（"平台建议：先 write_plan"），没有进入调度。
- 直接后果：多环节需求经常在没有任何计划的情况下开写；而"规划先行"一开又会对所有消息一刀切挂起。两个极端都不是用户要的。
- 业界对照：Codex 把审批策略与沙箱边界拆成两个正交控制面；Claude Code 的 plan mode 是权限状态 + 明确的退出选项，而不是人格切换。共同点是**默认最小、按任务爆炸半径升级、随时可覆盖**。

## 决策

1. **编排层不再是枚举，而是两个独立布尔门**：`needsPlan`（要不要先出计划并等批准）与 `needsReview`（交付后要不要过评审）。`TurnMode` 由两者派生（plan 优先），因此"先规划 + 后评审"可以组合。
2. **判定输出 `TurnIntent`**：`{ needsPlan, needsReview, risk, confidence, reasons[], source }`。`source ∈ user | rule | router | policy | default`，`reasons` ≤3 条、面向用户解释"为什么进规划"。
3. **三级流水**：
   - **L0 规则**（`server/src/orchestration/intent.ts#resolveIntent`，纯函数）：显式指令（"先出计划 / 直接做 / 评审一下"）、高风险动作、附件、复杂度信号、会话策略。零 LLM 调用；
   - **L1 结构化判定**：并入 PRS 的 `ROUTE_SCHEMA.intent`（**不新增任何模型调用**）。`@直达` 消息不走 PRS，只用 L0；
   - **L2 运行期纠偏**：写扩散（≥3 次写 + ≥2 成员）→ `intent:suggest-plan` 建议（**只提示，不强制改判**）。
4. **优先级**：用户显式 `mode` > 文本显式指令 > 会话策略（`autonomy` / 兼容 `planFirst`）> 复杂度推断 > 默认 execute。
5. **高风险强制规划**：`risk=high` 时不看置信度，始终 `needsPlan=true`（即使会话是 `never-plan`）。高风险词必须是**动作**（"部署到 / 正式发布 / 转账 / 签署"），不能误伤开发语境里的名词（"支付功能 / 发布页 / 删除接口"）。
6. **置信度阈值按风险不对称**（`applyConfidencePolicy`）：low ≥0.75、medium ≥0.55、high 强制。低置信度默认直接执行——误挂起是打断，误开写才可能不可逆；不可逆动作由工具审批门兜底。
7. **会话策略三态** `Session.autonomy: auto | always-plan | never-plan`（迁移 v36；`plan_first` 保留为兼容快捷开关）。UI：任务面板 chip 三态循环 + Composer 首 chip 由「执行」改为「自动」。
8. **判定全程可审计**：`run:start.intent`（重附着可恢复）、`intent:decided` 事件（PRS 合并后改判）、`intent:suggest-plan`（纠偏建议）、消息 `modeSource` 列（迁移 v37）、`trace: intent:decided`。前端在右栏运行面板展示来源 / 置信度 / 理由 / 两道门状态。
9. **右栏「运行」面板（Run Board）为唯一权威视图**：阶段条（研判 → 规划 → 待批准 → 执行 → 评审 → 收口）、判定依据、计划步骤与评审阻塞、待决策计数（待批准计划 + 工具审批 + 评审未通过）。聊天内计划卡保留操作能力，并加「运行面板」跳转；**不做自动抢视图**（复用 `setRightView` 的显式语义）。
10. **收口评审门**：`intent.needsReview=true` 且计划含 `acceptance / expectedOutput`、无显式 review 步骤时，计划完成后的作者收口波以 `review` 范式发言（`submit_review`），不新增步骤、不改计划谱系。
11. **灰度开关** `autonomyEnabled`（env `AUTONOMY_ENABLED`，默认开；设置面板「运行控制 → 自动编排」可关；关闭后回到旧语义：仅显式 mode / `planFirst` 生效，零差异）。

## M89 修订（实测驱动的规则收窄）

- **首波评审只给「纯验收」**：`TurnIntent.reviewFirst` 与 `needsReview` 分离。「整理求职规划并检查」先执行、交付后过评审门；只有无产出动作的「评审 / 验收一下」才直接进 review 范式（否则只读首波导致交付件缺失）。
- **复杂度只按阶段词**：顺序词 ≥2，或「长文本 + 顺序词 + 多交付物」；不再把「后端 / 接口 / 测试」等开发名词当复杂度信号（曾导致普通实现需求被强制规划）。
- **高风险只收「动作」**：「正式发布 / 发布到 / 部署到 / 签署 / 提交申报」；「发布日历 / 报税检查 / 支付功能」不算。
- **「先出计划」需确认语义**：「先出计划给我看 / 先出计划再动手」才算；「先制定照护方案」是产出动作。
- **评测夹具显式 `relay=auto`**：eval 验证链路能力，不受单助手 `manual` 默认影响（否则会误判为回归）。

## 理由

- **把"选模式"变成"看依据"**：用户只需在看不懂时打开运行面板，而不是每次发送前做一次预判。
- **零额外调用**：判定并入 PRS 已经发生的那一次结构化调用，成本只在 `@直达` 路径（纯规则）。
- **误判可撤销**：显式 chip 永远最高优先级；PRS 判定只在无 @ 的首波生效；运行期只给建议不强制改判。
- **语义正交**：`needsPlan` 与 `needsReview` 独立，解决了旧三选一无法表达"先拍板、后验收"的组合。
- **审计闭环**：`modeSource` + `intent:decided` + 运行面板，让"为什么这次先出计划"随时可回答。

## 被否决的方案

- **纯 LLM 分类器每次调用**：多一次延迟与成本，`@直达` 路径无法承受；且不可解释。
- **让 agent 自己决定要不要规划**（模型自调 `request_plan`）：判定发生在"已经开始写"之后，FN 不可挽回，且无法在首波派发前决定队列。
- **保留三 chip 再加一个"自动"**：认知负担没减（仍要理解三种模式的区别）；改为"自动"为默认 + 两个显式覆盖。
- **高风险词按名词匹配**：实测把"设计一个支付功能 / 把发布页做出来"误判为高风险并挂起（engine 用例超时），因此收紧为动作短语。
- **低风险也按 0.5 阈值规划**：会把大量普通需求变成挂起；采用按风险分档的阈值。
- **评审门自动插入计划步骤**：改变计划谱系与派发队列，风险高；改为"作者收口波 review"的轻量门。

## 适用与失效条件

- 适用：单会话内人机同席；判定输入为用户最新一条消息 + 会话策略 + 计划状态；`@直达` 消息只走 L0。
- 失效条件：多人同时改同一会话的编排策略需以会话属主为准（当前 PATCH 仅属主）；判定准确率依赖规则词表，领域扩展（如医疗 / 法律）应补类别词而非放宽全局阈值；若引入"按角色默认范式"，需要把 `autonomy` 扩展为角色级策略叠加。
