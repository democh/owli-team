# ADR 0057：SRE 场景与 SSH 事故响应管道（SRE Agent & SSH Incident Response）

- 状态：Accepted
- 引入：M32
- 相关：[design.md §47](../design.md)、ADR 2（handoff 工具优先）、design.md §21（工具系统与 Harness）、ADR 14（工作区沙箱）、ADR 23（HITL 审批）、ADR 31（场景协议分层）、ADR 42（连接中心与凭据加密）、ADR 44（SSH 交互终端）、ADR 54（工具按需发现）、ADR 55（编码代理能力基线）

## 背景

- M22 / M23 已建成 SSH 远程执行能力（连接中心凭据加密 / 会话绑定 / `allowExec` 连接级开关 / 审批门 / 30s 超时与 256KB 截断；「终端」页签提供交互式 xterm 会话），但**生产运行态没有专职角色**：devops（奥托）管发布与交付（白名单含 `ssh_exec`），面向的是「变更交付」而非「运行态保障」——事故分级、止血纪律、证据链与无责复盘没有资产承载。用户提出「结合 SSH，实现一个专业的 SRE 的 Agent」。
- 三类缺口：
  1. **角色缺位**：无 SRE 场景与可靠性角色——「告警 → 分级 → 止血 → 定位 → 复盘」的事故响应链路没有编制承载；devops 的交付职责与事故响应混用会让「变更者」与「稳定性守护者」的角色边界模糊（「变更即可疑」原则要求审查路径独立于变更路径）；
  2. **发现路径缺失**：`ssh_exec` 为 `tier='deferred'`（ADR 54），角色白名单授权后模型初始不可见——若方法论文档不引导 `tool_search` 激活，会出现「授权了但不知道能激活」的能力空转（M30 同款风险）；
  3. **事故方法论缺失**：SEV 分级标准、止血纪律、SSH 只读诊断命令库、时间线与度量（MTTD / MTTA / MTTR）、无责复盘模板散落无归处，协议层与技能层均无对应资产。
- 硬约束：
  1. **零新增工具代码**：只做「已建成能力的角色绑定 + 方法论文档」，不改 `ssh_exec` 实现与引擎；
  2. **权限边界**：SRE 面向运行态诊断，不提交代码（git 只读）——与 qa 的 `db_*` 只读三件套同先例；
  3. **延迟披露兼容**：`ssh_exec` 保持 `deferred`，经 `tool_search` 激活后本 Run 可用（ADR 54 语义不变）；
  4. **零回归**：mock / eval 不依赖新增可见性；改后 `check:agents` / `check:skills` / `eval` / vitest 全绿。

## 决策

1. **新增 sre 场景**（单角色编制，同 wealth / travel / bi 先例）：id `sre` / 站点可靠性 / icon `activity` / theme `#84cc16`（lime，第 17 个场景色）/ order 15（development 与 brainstorm 之间——可靠性职能紧跟研发）/ chain `[sre]`。
2. **SRE 工程师（江屿）工具白名单**：文件集（`list_dir` / `read_file` / `write_file` / `edit_file` / `apply_patch` / `search_text` / `glob` / `grep`）+ **SSH 远程执行**（`ssh_exec`）+ 本地验证（`run_command`）+ **git 只读三件套**（`git_status` / `git_diff` / `git_log`，不含 `git_branch` / `git_commit` / `git_restore`）+ 度量与检索（`calc` / `date_calc` / `web_fetch` / `web_search`）+ 协作基线（`write_todos` / `load_skill` / `remember` / `handoff` / `request_approval`）；handoff `[devops, backend, qa]`。
3. **事故响应六步法**（技能层承载）：分级与止血（SEV1-3 + 恢复优先）→ 证据采集（`ssh_exec` 只读命令库逐条记录 exit code 与输出摘要）→ 定位（变更即可疑 → 资源 → 依赖）→ 修复与验证（报批 + 观察窗口）→ 复盘（时间线 + 5 Whys + 改进项四要素）→ 沉淀（SLO 口径 `remember` + runbook）。
4. **场景协议 `agents/sre/_protocol.md`**（七条铁律 + 协作三条）：① 证据先行；② 止血优先变更报批；③ SSH 使用纪律（只读优先 / `tool_search` 引导 / 单条非交互与超时意识 / 绑定提示）；④ 变更即可疑；⑤ 时间线纪律（统一时区 + 证据出处）；⑥ 复盘无责；⑦ 数据安全脱敏；⑧ 分工（运行态 vs 发布 vs 修复 vs 验证）；⑨ 与 development 场景交接；⑩ 数据丢失风险处置先 @用户 确认。
5. **技能层**：新增 `skills/incident-response`（SEV 分级表 + 五步响应 + SSH 诊断命令库 + 定位检查表 + 度量 + 复盘模板 + SLO / 错误预算 + 反模式）；sre 预载两技能（`incident-response` / `debugging`）；技能库 40 → 41。
6. **三处 `tool_search` 引导**：AGENT.md 职责与工作方式、场景协议第 3 条、incident-response 技能均显式写明「先 `tool_search` 检索『SSH / 远程 / 日志』激活再使用」；`<tool_discovery>` 区块「SSH 远程」分组概览提供发现面兜底。
7. **审批门纪律上收协议**：`ssh_exec` 每次调用均经审批门（引擎语义），协议层明确「审批 ≠ 免责」——变更类命令仍须说明影响范围与回退方式；`allowExec` 未开启时按提示路径引导开启。
8. **预设与测试**：快速组队预设 +1（`incident-response`：sre 止血 → devops 回滚 → backend 修复 → qa 回归）；新增 `server/tests/m32-sre.test.ts`（16 断言，含运行时绑定与范式收敛）；`m21.test.ts` 适配 17 场景 / 68 角色 / 12 预设。

## 理由

- **接通优于新建**（与 M29 / M30 同模式）：M22 / M23 已建成 SSH 连接与执行链（凭据 / 绑定 / 开关 / 审批 / 超时 / 截断），缺的只是「角色绑定 + 方法论文档」——新增成本集中在资产层，无工具代码与引擎改动；
- **变更者与守护者分离**：SRE 主导事故响应而 devops 执行发布——「变更即可疑」要求审查路径独立于变更路径；SRE 不持 git 写类工具使这一原则在权限层落地，而非仅靠提示词自律；
- **只读边界与 qa 先例一致**：SRE 的诊断动作（状态 / 日志 / 磁盘 / 内存 / 端口 / 健康检查）全部由只读命令覆盖；代码修复经 `handoff` 交 backend，权限模型不越界；「存在但不可达」与「可达但越权」两类历史缺陷同时规避；
- **方法论文档三处引导**：`deferred` 工具的核心风险是「授权了但不知道能激活」——LLM 需在角色正文、场景协议、技能正文多个语境反复看到激活路径才能形成稳定行为；
- **场景=职能域**：可靠性是跨场景职能（任何有生产系统的会话都可能是需求方），独立场景比并入 development 编制链更符合组织语义；order 15 紧跟 development，保持「研发 → 可靠性」的语义相邻；
- **单角色场景先例**：职责聚焦（运行态保障），无需编制链；后续若需要「容量规划师」「混沌工程专家」可在 sre 场景内扩张。

## 被否决的方案

- **并入 development 场景作为第 14 个角色**：development 编制链（pm → architect → … → devops）是「需求 → 交付」的生产流水线，SRE 的「告警 → 复盘」是运行态回路，混编会让默认组队与接力叙事失真（同 bi 独立场景的理由）；
- **SRE 授予 git 写类 / 发布工具（成为「能修能发」的全能角色）**：违背变更者与守护者分离原则；修复行为需经代码评审与回归（backend / qa 职责），发布需经流水线（devops）——SRE 的产出是「证据链 + 处置决策」，不是代码提交；
- **新增 `sre_*` 专用工具**（如指标查询 / 告警管理 / 部署编排 API 集成）：需要新增外部系统集成与凭据模型，违反零新增依赖；`ssh_exec` 的通用性（凡 SSH 可达的环境皆可诊断）已覆盖主要场景，专用集成留给后续里程碑按需评估；
- **`ssh_exec` 改 `core`（常驻可见）**：违背 ADR 54 的渐进披露设计——SRE 会话中相当比例的回合在做复盘文档 / SLO 核算（纯文件与计算侧），`ssh_exec` 常驻会让每轮工具 schema 白付 token；`tool_search` 激活一次即本 Run 可用，成本更低；
- **把事故响应提示词硬编码进引擎**（如自动注入「先止血」前缀）：违反资产化原则（agents/ 与 skills/ 是热更新资产，改行为无需改代码重启）；M15 以来的资产包体系即为此设计；
- **SRE 白名单含 db 工具（含只读三件套）**：数据侧取数归 bi 场景、数据修复归 data-engineer；SRE 的数据库侧诊断（连接数打满 / 慢查询）经 SSH 侧 `ss` 与数据库客户端命令可达，无需直接持有 `db_*`；
- **预设成员含观察者角色**：事故处置需要「执行链路」而非「评论链路」——sre 止血、devops 回滚、backend 修复、qa 回归四角色构成闭环，增加观察者只会稀释行动密度。

## 适用与失效条件

- 适用：本地单用户部署（与 ADR 42 / 44 / 53 / 54 同一产品形态）；已绑定 SSH 连接且开启「允许 Agent 执行命令」的会话（未绑定时应收到「右侧面板「连接」页签绑定」提示而非报错）；生产事故 / 容量评估 / SLO 类任务。
- 失效条件：
  - 引入多用户 / 多租户共享实例时，SSH 连接的会话绑定与审批模型需升级为按用户隔离；
  - 若未来 SRE 需要执行自动化修复（auto-remediation / 自愈脚本），须重新评估审批模型与最小授权，并回改本 ADR 与场景协议第 2 条；
  - 若接入外部监控系统（指标平台 / 告警系统 API），工具层需要新增集成时，本 ADR 的「零新增工具代码」前提失效，须重新评估；
  - 若模型在 `tool_search` 缺失语境下频繁漏激活 `ssh_exec`，应增强 `<tool_discovery>` 区块的 SSH 分组提示，而非把工具改回常驻；
  - 技能库继续扩容至系统层预算阈值时，sre 的两预载应回归按需加载并重新评估索引摘要长度（对齐 ADR 55 / 56 失效条件）。
