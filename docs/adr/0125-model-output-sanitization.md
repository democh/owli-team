# ADR 0125：模型输出净化与落盘声明审计——仿写日志块剥离 · 协议标记泄漏清理 · 双端兜底

- 状态：Accepted
- 引入：M55
- 相关：[design.md §77](../design.md)、ADR 0113（专业排盘卡与协议记录真实性红线）、[shared/src/sanitize.ts](../../shared/src/sanitize.ts)、[server/src/orchestration/engine.ts](../../server/src/orchestration/engine.ts)、[client/src/stores/session-store.ts](../../client/src/stores/session-store.ts)、[server/src/context/assembler.ts](../../server/src/context/assembler.ts)

## 背景

- 用户实测截图（会话 s_a1a972a1）：聊天气泡出现 `[工具调用]` 文本块、`ziwei_pan({...})` 原始 JSON 参数与「紫微排盘完成」摘要——该消息 tool_calls 为空、run 事件零工具调用，**模型在正文仿写了系统内部的上下文投影格式**（assembler 注入历史真实调用的 `[工具调用]\n- 名称(参数) → 摘要` 段落）；
- 同会话另一条消息：正文两处声称 write_file「已写入 3.9KB」，但 run 事件无任何成功写调用——**编造成完成态落盘声明**；正文并泄漏 `</…DSML…>` 形态的协议标记行（全角竖线包裹的 `｜｜DSML｜｜`，模型工具协议标记以纯文本泄出）；
- M53（ADR 0113）已立「记录真实性」prompt 红线，但实测 deepseek-flash 仍会仿写与泄漏——**prompt 约束不可靠，需代码级兜底**；
- 边界：存量消息已在数据库中（含脏文本），本批不动库（前端展示层过滤）；新消息在落库前净化。

## 决策

1. **净化函数下沉 shared**（`sanitizeModelText`）：规则**宁窄勿宽 · 半截流式安全 · 幂等**——
   - `[工具调用]` 独立行 + 其后连续（空行 / 列表行 / 缩进续行）序列：仅当序列含 ≥1 条带箭头（→ / -> / =>）日志行时**整块删除**；无日志行 = 流式半截 → 保持原文待补齐整体命中；无标题行时单靠箭头不剥离（正常箭头列表不受影响）；
   - 协议标记行（整行匹配 `</?｜…DSML…`）整行删除（半截不匹配待补齐）；
   - 删除造成的多余空行归一（≥3 换行压 2）+ 尾部空白去除；无命中原样返回（快速短路）。
2. **服务端收尾净化为落库唯一真相**（engine `sanitizeAndAudit`，幂等挂 6 处收尾点：executeTurn 的 parseMentions 前与 catch、finishTurn、续写 / 重生成完成、异常 / 中断 catch）——内存对象即净 → 落库 / FTS / 记忆沉淀 / 下一回合上下文装配全干净，防模型看到自己脏文本形成自我强化循环；净化先于 @ 解析（仿写块内可能出现伪 @ 交还标记）。
3. **落盘声明审计**（`extractDeliveredPaths` + `sanitizeAndAudit` 内比对）：完成态声明（已写入 / 已落盘 / …；裸「落盘」须紧跟冒号）后 60 字符窗口内文件路径 vs 成功写调用（status=ok 的 args.path / args.output）——不符 → trace `delivery:unverified` + logger.warn **留痕不阻断**、不改正文（不替模型「纠错」，只给运维与评测留证）。
4. **前端展示兜底**（session-store）：toStores（加载 / 刷新）与 upsertMessage 对 role=agent 净化（存量消息历史回看直接干净）；流式 appendDelta 保留**原始累积缓冲**（rawStreams）对「原始全文」求净化写回 content；turn:start（续写 / 重生成复用消息 id）重置缓冲、回合收尾释放、会话切换清空；用户消息豁免（引用系统格式属正常输入）。

## 理由

- **投影格式与用户可见内容必须分离**：`[工具调用]` 段落是上下文投影的内部表示（真实调用日志的展示形态），出现在正文中必然是仿写；整块删除的证据要求（≥1 条带箭头日志行）把误伤面压到「正文恰好复刻内部格式」这一本身就不该发生的情形；
- **收尾点净化优于逐个消费端净化**：落库 / FTS / 记忆 / 上下文装配共用同一内存消息对象——收尾时净一次，全部下游干净（只做前端过滤会留下脏数据继续污染模型后续回合）；
- **流式必须对原始文本求净化**：块删除以标题行锚定，若对已净化文本增量拼接，块内后续日志行会失去锚点成为孤行（client 测试有专项回归）；
- **审计留痕而非阻断/改写**：声明真伪的最终判定成本高（工具别名 / 间接写路径）；trace + warn 保留证据链，为后续评测与协议加固提供数据，不引入误伤正常正文的风险；
- **零 agents 资产变更**：M53 红线条款已覆盖此类行为，本批是代码级执行层兜底，不动 prompt。

## 被否决的方案

- **仅前端过滤（不动服务端）**：脏文本继续落库 → FTS / 记忆沉淀 / 下一回合上下文全被污染，模型自我强化；
- **仅调 prompt（M53 路线加强）**：已实测不可靠；且历史脏文本仍会被装配进上下文继续示范；
- **正则全局删除所有箭头列表行**：误伤正常正文（普通 markdown 列表 + 箭头），违反宁窄勿宽；
- **净化时改写落盘声明（如追加「未验证」标注）**：替模型改口径，破坏正文原貌与用户信任；留痕交给 trace / warn；
- **存量数据库内清洗（迁移脚本）**：需重放判定且不可逆；展示层过滤即可达到用户可见效果（用户选择「前端过滤即可」）。

## 适用与失效条件

- 适用：所有 agent 消息的正文展示、落库与上下文装配；规则针对 `[工具调用]` 仿写块与 `｜｜DSML｜｜` 系协议标记；
- 失效条件：投影格式若变更（如 `[工具调用]` 标题改版 / 箭头形态变化），净化规则须同步更新（常量集中在 `shared/src/sanitize.ts`）；声明锚词表（已写入 / 已落盘 / …）随协议扩展补词；
- 已知边界：块内续行若在流式窗口内以「无标题孤立箭头行」出现（历史脏数据截断等极端情形）不剥离（宁窄勿宽）；`delivery:unverified` 为启发式留痕，存在漏报（声明含蓄时）与误报（工具别名路径）可能，不作阻断依据。
