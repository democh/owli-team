# ADR 0223：接力控制（自动 / 手动）与用户派发

- 状态：Accepted
- 引入：M86
- 相关：[ADR 0048](0048-turn-modes-and-plan-approval.md)（回合范式与计划审批）、[ADR 0049](0049-plan-dispatch-task-board.md)（计划派发与任务面板）、[ADR 0033](README.md)（并行波次）、[ADR 0011](README.md)（SSE + WS 双通道）

## 背景

- M16 / M48 建立的「成员自主接力」是多 Agent 协作的核心：成员在发言末尾通过 `handoff`（或正文 @）把下一棒交给其他成员，引擎在波末合并队列，未在场角色还会被自动召集。
- 但这套默认在**对话场景**里不符合预期：单助手会话里一句"这块让设计看一下"就会把设计 agent 拉进会话并继续消耗回合；私聊 / 群聊形态也可能误触。用户无法在事前阻止，只能事后停止。
- 现有两个开关都管不到这件事：`routeMode`（M79-E）只管"未 @ 的用户消息是否交给平台路由"；`planFirst` / 消息级 `mode`（M24）只管本回合的规划 / 评审范式。**「agent 之间是否自动接棒」没有独立控制面。**

## 决策

1. **新增会话级接力控制** `Session.relay: 'auto' | 'manual'`（`sessions.relay_mode`，迁移 v34；NULL = 未显式设置）。
2. **默认按会话形态推导**（`shared/src/members.ts#resolveRelayMode`，前后端共用）：
   - `direct` / `group`（人与人的对话）→ `manual`；
   - 单成员编制（单助手对话）→ `manual`；
   - 零编制（待平台组队）与多成员 team → `auto`（零编制若判 manual，PRS 召集出的人也无法接力，开场即死）；
   - 显式设置永远优先。
3. **manual 下 `handoff` 降级为「建议」**：工具仍可见、仍返回 `ok`（模型得以结构化表达"应该由谁接"），但回执改为「已记录派发建议 @X，等待用户点按派发」；引擎不投递便条、不自动召集、不把目标写入下一波队列，并落 `handoff:suggested` 审计事件。波末合并再加一道保险（`accepted = []`、`handedToUser = true`），防未来新路径绕过。
4. **用户派发是 manual 的唯一接棒入口**：`engine.dispatchTo(sessionId, agentId, { note? })` + `POST /api/sessions/:id/dispatch`：
   - 活跃 Run → 目标插到队首（不打断当前发言人），广播 `queue:updated`；
   - 空闲 → 新起一个 Run（队列 = [目标]，**跳过平台路由**，不再重新组队）；
   - 落一条系统事件条（「你派发了下一棒给 X」）+ 派发便条（注入目标回合指令的「上一棒期望」）；
   - 权限与发送消息同口径（非 viewer）；目标必须是会话在场成员。
5. **UI 入口**：会话头「自动接力 / 手动接力」开关（有 agent 编制且为属主时可见）；消息菜单「派发下一棒」（agent 消息可见），并把该条消息 `handoff` 工具建议的目标**置顶标注「建议」**，一次点击即派发；viewer 不渲染派发入口。
6. **计划派发不受 manual 影响**：批准后的计划仍由 `dispatchApprovedPlans` / `refillPlanQueue` 按步骤负责人推进——那是用户已经拍板过的执行，不属于"agent 自主接力"。
7. **零差异**：`auto` 路径与既有实现完全一致；`relay` 缺省不落字段；能力不删除，只改默认与入口。

## 理由

- 与业界成熟做法同构：Codex 把「审批策略」与「沙箱边界」拆成两个正交控制面，Claude Code 把 plan mode 做成"权限状态 + 审批选项"而不是人格切换。**自动化的可信度来自"默认最小、随时可覆盖"**，而不是把能力删掉。
- 单助手对话的高频诉求是"先把这件事说清楚"，不是"再拉三个人开个会"；把自动接力收敛掉，能显著降低意外回合与 token 消耗。
- 保留 `handoff` 工具的"建议"语义，比直接隐藏工具更好：模型的结构化判断仍有出口，UI 能把它变成一键操作（人机协作的最小摩擦）。
- 不新增 Run 状态：用"交还用户 + 用户派发新 Run / 插队"承接，避免 `awaiting_handoff` 引入第二套挂起 / 停止 / 重附着逻辑。

## 被否决的方案

- **全局关闭自动接力**：破坏多成员团队的核心协作能力（M16 全链推演、M42 例会、M48 派发都依赖它）。
- **manual 下隐藏 `handoff` 工具**：模型失去表达下游的通道，只能写自然语言，UI 无法结构化呈现"建议下一棒"。
- **新增 `awaiting_handoff` 挂起态**：状态机与审批 / 计划挂起叠加，重附着与超时语义重复，收益不抵成本。
- **客户端伪造一条用户消息来触发派发**：污染会话历史与 token 预算；服务端 `dispatch` 用系统事件条留痕更干净。
- **把接力控制塞进 `routeMode`**：两者作用面不同（用户消息 vs agent 之间），合并会让"仅点名唤起"的语义不可解释。

## 适用与失效条件

- 适用：单用户决策面；派发目标为在场成员（跨场景增员请先邀请）；manual 下仍允许用户消息 @ 直达（那是用户显式意图，不是 agent 自主接力）。
- 失效条件：多人同时派发同一会话需补并发策略（当前"后到者置队首"）；若未来需要"团队内自动、跨场景需确认"的细粒度策略，应把 `relay` 扩展为规则集而非二值。
