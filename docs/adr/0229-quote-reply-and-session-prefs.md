# ADR 0229：引用回复与会话个人偏好（置顶 / 免打扰）

- 状态：Accepted
- 引入：M90
- 相关：[ADR 0228](0228-im-message-reliability.md)（消息可靠性）、[ADR 0188](0188-user-topic-and-inbox.md)（用户主题）、[ADR 0194](0194-people-sessions-kind-and-dm.md)（人物会话）

## 背景

M90 第一批把发送、补偿、已读收紧后，聊天仍缺少两项「专业 IM 的日常语义」：

1. **回复没有结构**：消息菜单的「引用到输入框」只是把原文转成 Markdown 引用块，接收方看不到「回复的是哪一条」，原消息删除后上下文彻底丢失。
2. **会话没有个人排序与静默**：所有会话按 `updated_at` 排列，繁忙会话会长期占据首位；没有免打扰时，任何一条人类消息都会弹 toast / 系统通知，打断当前工作。

两者都必须**只影响本人**，不能改动会话 ACL、消息可见性或他人的列表顺序。

## 决策

1. **引用回复用服务端快照，不存外键联查**
   - 发送体新增 `replyToMessageId`（可选，必须能由服务端在本会话解析）。
   - 消息新增 `reply_to`（迁移 v40），保存 `{ messageId, authorName?, excerpt }`；摘要在发送时由服务端重算并截断 120 字，**不信任客户端摘要**。
   - 快照在发送时固化：原消息后续被编辑不会改变引用内容；原消息被删除后仍可展示摘要。
   - 目标在点击回复后被删除、或 ID 不属于本会话 → 落墓碑快照 `{ messageId, excerpt: '原消息已删除', deleted: true }`，**仍允许发送**。用户表达不因竞态丢失。
   - 读取时投影 `deleted`：`SessionStore.get()` 按当前会话消息集合校准；运行期删除同时把内存中指向它的引用标为已删除。客户端不靠「本地是否加载到原消息」推断（分页下会误判）。
   - 幂等摘要包含 `replyToMessageId`：同一提交标识换引用目标视为不同请求（`409`），避免重试把引用悄悄改掉。
2. **引用只对当前会话有效**
   - 客户端 `ui-store.replyTarget` 保存目标；切换会话、发送成功或点击取消即清除。
   - 待发箱持久化 `replyToMessageId`，断网重试仍引用同一条；崩溃恢复不自动重发。
3. **会话个人偏好按用户存**
   - 新增 `session_prefs`（迁移 v40）：`(user_id, session_id) → pinned / muted`；不改 `sessions` 行，不参与 ACL。
   - `PATCH /sessions/:id/prefs` 只允许本人；返回投影并通过用户主题发 `notify:session-prefs` 做多端同步。
   - 会话列表随行返回 `prefs`（无记录 = 均关），客户端置顶优先排序、组内保持服务端 `updated_at` 顺序。
4. **免打扰的边界**
   - 仅抑制普通消息的 toast / 系统通知；**未读计数照常累加**，徽章改为静音色。
   - 收件箱事件（邀请 / 提及 / 待回复）仍提醒——静默的是「聊天刷屏」，不是「需要处理的事」。
   - 不提供「静音后清零未读」：那会让用户永久错过消息。

## 理由

- **快照优先于联查**：引用需要跨删除、跨分页稳定展示；联查原消息会在删除后变成死链，也会让历史页的引用依赖未加载的数据。
- **墓碑而非 400**：引用目标在「点击 → 发送」之间被删是正常竞态。拒绝发送会让用户重写一遍；墓碑保留「我在回复什么」的语义。
- **偏好独立成表**：置顶 / 免打扰是收件人视角，不是会话属性；写进 `sessions` 会污染他人的列表与审计语义。
- **排序在客户端**：服务端列表继续以 `updated_at` 为稳定事实源；置顶只改变当前用户的展示顺序，避免分页 / 缓存与多端排序口径分裂。
- **免打扰不等于隐藏**：保留未读与收件箱提醒，维持「不丢消息」的总原则。

## 被否决的方案

- **客户端提交引用摘要 / 作者名**：可被伪造，且原消息编辑后会产生与正文不一致的引用；服务端重算成本极低。
- **引用目标不存在直接 400**：把竞态变成用户可见失败；墓碑更符合 IM 习惯。
- **回复使用外键 + JOIN 实时读取**：删除后引用消失，分页时还要额外查询未加载消息。
- **把 `pinned / muted` 写进 `sessions` 表**：多人会话下会互相覆盖；也破坏「会话元数据对所有成员一致」的既有语义。
- **服务端按置顶重排列表**：需要把个人偏好混入全局排序与分页游标；客户端稳定排序已满足需求。
- **免打扰时不再累计未读**：用户会失去「有消息待看」的信号；与 M79「未读服务端权威」冲突。
- **免打扰同时静默 @提及 / 邀请**：这些是需要行动的事件，静默会造成协作事故。

## 适用与失效条件

- 适用：当前「一切皆会话」模型；单用户兼容模式（偏好接口 400 / 无账号语义）与多用户模式。
- 失效条件：
  - 引入「会话级全员公告 / 全员置顶」时，需要区分个人偏好与会话属性，另建字段与权限；
  - 若消息支持富文本 / 附件引用卡片，`excerpt` 需升级为结构化引用（类型 + 资源 id），并重评 120 字截断；
  - 若未来支持「回复也随原消息编辑而更新」，当前快照语义需改为引用版本号 + 可选联查；
  - 若引入服务端离线推送，`muted` 需要同步到推送网关，而不是只在客户端抑制 toast。
