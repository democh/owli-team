# ADR 0043：操作直播窗（LiveDock）与双视图联动（M22）

- 状态：Accepted
- 引入：M22
- 相关：ADR 42（连接中心与 CDP 浏览器接入）、ADR 5（SSE 流式通道）、ADR 11（SSE + WS 双通道）

## 背景

ADR 42 让 Agent 能操作浏览器与数据库，并提供了右栏「浏览器 / 连接」面板。真实使用暴露四个盲区：

1. **右栏窄栏看画面**：帧流塞进 26% 宽的右栏，细节看不清；
2. **跨页签盲区**：用户切到主区写消息 / 看交付件时，完全看不到 Agent 正在浏览器里做什么；
3. **数据库操作是「黑盒」**：db_* 只有事后审计流水，没有实时过程；
4. **空态信息弱**：浏览器面板空态只有一个下拉 + 按钮，三种接入方式的差异（本机 / 无头 / 远程）没有解释。

用户明确要求：「悬浮一个 div 窗口来展示，可以拖动……设计一个优雅的不遮挡、有联动的交互」，并确认两个方向：**双视图（右栏美化 + 悬浮直播窗）+ 首次实况操作自动滑入**。

## 决策

**一个 store（`live-dock-store`）+ 一个浮层容器（`LiveDock`），与右栏面板形成「控制中心 / 实时直播」双视图分工**：

- **三态生命周期**：卡片（默认 420×320，范围 320–720 × 200–640）↔ 胶囊（280×36 摘要条）↔ 关闭（= 本次运行静音）；胶囊回落保留复盘入口，成本仅一条；
- **不遮挡策略**：默认锚定右下（margin 16 + 底部 88px 避让 composer）；视口 > 900px 时锚点再左移右栏宽（≈26% 视口的启发式）；`z-40`（在命令面板 / Dialog 之下）；toast 在 top-center 天然错开；拖动 / 缩放全程 clamp 在视口内；松手 14px 内吸附边缘；Esc 折叠为胶囊（输入框内不响应）；位置尺寸 localStorage 400ms 防抖持久化；
- **自动滑入（事件驱动）**：`notify:op` 到达且 `kind ∈ {browser, db}` → 首次展开卡片并选中对应 tab；同一 Run 只弹一次（`autoRunId`）；「关闭」= 本次运行静音，`notify:run-started` 重置静音；`run-completed / error / awaiting-user` 后 3s 回落胶囊（新操作取消回落）；用户手选 tab 后 60s 内不被操作类型抢切；
- **数据源零同步**：浏览器帧 / 步骤直读 `browser-store`，数据库操作直读 `connections-store.ops`——右栏与浮窗是同一 store 的两个视图，没有跨组件同步代码；
- **流所有权引用计数**：`browser-store` 模块级 `viewHolders`，右栏面板与直播窗各自 `retainView / releaseView`，归零才 `detach`——一方卸载不再误杀另一方的帧流；
- **服务端补事件**：数据库工具经 `ToolRuntime.opNotify` 钩子发布 `notify:op`（含 `preview`：查询结果前 5 行），工具层保持 notify 无关性，信封字段由引擎补齐；
- **输入桥共用**：坐标换算 / 滚轮 non-passive / 键盘直通的 `useBrowserFrameInput` 由右栏与直播窗共享，行为天然一致；
- **手势零依赖**：Pointer Events + rAF 节流（`use-drag.ts`），clamp / snap 为纯函数可独立单测，不引入 react-draggable 等依赖。

## 理由

- **悬浮窗而非模态**：模态抢焦点、中断阅读与输入；直播是「余光可见」的陪伴式信息，不该有阻断性；
- **胶囊而非隐藏**：运行结束后「刚才 Agent 干了什么」仍有回溯需求，36px 的摘要条是保留入口的最低成本；且胶囊保留拖动位置，用户摆放意图不丢；
- **事件驱动自动滑入而非常驻**：常驻浮窗在无操作时纯属遮挡；`notify:op` 是「正在发生」的最准信号（比 run-started 晚一点，但不会在纯聊天 Run 里误弹）；
- **同一 Run 只弹一次 + 静音语义**：自动弹出是打扰，用户一旦关闭就说明「这次我不想看」，尊重到 Run 结束（新 Run 重置）；
- **引用计数而非「面板卸载即断流」**：双视图下断流时机不再等于任何单一组件的生命周期，计数是最小正确模型；归零才断也避免了「右栏 → 直播窗」切换瞬断；
- **数据库 tab 读 connections-store 而非新通道**：浏览器事件已有 `notify:op`，数据库补齐到同一事件流，前端零新协议；`preview` 只带前 5 行——直播窗要「看得见」，完整结果在右栏 / 审计里；
- **右栏宽度启发式（26%）而非精确测量**：精确读取 PanelGroup 尺寸需跨组件共享布局状态，26% 与 `Panel defaultSize={26}` 一致，误差（用户拖过分隔条）只影响默认锚点的美观度，拖动一次即覆盖。

## 被否决的方案

- **单视图（只美化右栏）**：跨页签盲区是核心痛点，右栏无法回答「切走时 Agent 在干什么」；
- **模态 Dialog 直播**：阻断性；且用户在看直播时往往同时在写消息 / 翻交付件；
- **Document Picture-in-Picture API**：浏览器支持面不全（Safari 无、Chrome 需近期版本），样式能力受限（无 backdrop-blur 等），且原生窗口无法与右栏做「查看详情」联动；
- **默认居中 / 左上浮窗**：遮挡主内容；右下 + 底部避让是最不打扰的象限（聊天输入区在底部中间，避让 88px 即可错开）；
- **拖拽引入 react-draggable / interact.js**：Pointer Events 原生 + rAF 节流 150 行内可解，clamp / snap 纯函数由单测覆盖（20 例），符合零新增依赖纪律；
- **数据库 tab 用独立 WebSocket / SSE 通道**：协议重复、连接数翻倍，收益为零；
- **浮窗持久化「展开/折叠状态」**：刷新后从关闭开始是刻意选择——上次会话的浮窗状态对新的上下文没有意义，位置 / 尺寸持久化已覆盖「用户摆放意图」。
