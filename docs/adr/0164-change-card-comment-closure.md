# ADR 0164：变更卡与意见闭环——摘要与跳转边界 · 高置信配对（AF-2 / AF-3 / AF-4）

- 状态：Accepted
- 引入：M44 核心交付锚点范式（2026-09-19）
- 相关：[design.md §101](../design.md)、[docs/scene-chat-design.md §12](../scene-chat-design.md)（M44 原案；决策项 0079 / 0080 落位）、ADR 0079（聊天流只做摘要与跳转——本 ADR 为其在变更语义上的落地）、ADR 0080（闭环推导宁缺毋滥）、ADR 0062（容器/派生优先）、[client/src/components/chat/ChangeCard.tsx](../../client/src/components/chat/ChangeCard.tsx)、[client/src/components/chat/DeliveryList.tsx](../../client/src/components/chat/DeliveryList.tsx)、[client/src/components/chat/MessageActions.tsx](../../client/src/components/chat/MessageActions.tsx)

## 背景

- M44 原案：AF-2 变更卡（消息内嵌，与 DEV-2 合并卡族：「文件 + vN 徽章 + 增删行摘要 + 作者；点击 → 交付件 Tab + Diff」）；AF-3 提意见入口（消息菜单 / 锚定条，「@作者 对 <交付名> 的意见：」模板）；AF-4 闭环配对展示（变更卡角标「回应了你 v2 的意见」；锚定条未闭环计数；低置信不展示）；
- 依赖已于 M39 就绪：DEV-2 交付明细行（ArtifactRow：作者 / 阶段 / 悬停预览）与 ADR 0123 分层；`artifacts/versions` 与 `artifacts/diff` 接口为既有能力。

## 决策

1. **AF-2 变更卡（卡族合并而非新卡）**：消息「产出交付件 + 伴随写类工具调用（write_file / apply_patch / edit_file）」时，交付明细行升级为「变更」语义——**复用 ArtifactRow**（新增两个可选项：`version`（vN 徽章，版本列表懒加载）与 `trailing`（行尾槽位）），头部「变更 · N」；点击行 → 打开交付件（完整 Diff 在交付件工作台——ADR 0079 边界：聊天流只做摘要与跳转，**不做**内联完整 Diff）；
   - **增删行摘要按降级链处理**：当前渲染「文件 + vN + 作者（+体积）」；行级增删统计需逐版本 diff 拉取（N 次请求），**不作为默认路径**（原案已注明「diff 统计缺失→仅文件与版本」）；若未来版本接口携统计字段再点亮。
2. **AF-3 提意见入口**：成员消息菜单新增「提意见（对交付件）」（仅消息含 artifacts 时出现）——写入草稿 `commentDraft(authorName, path)`（「@作者 对《交付名》的意见：」；无作者退化为「对《交付名》的意见：」；只写草稿不直发，ADR 0064）；锚定条操作区同模板。交付名用**含扩展名**的文件名（避免同名主干歧义；解析端兼容主干匹配）。
3. **AF-4 闭环配对（宁缺毋滥，ADR 0080）**：
   - **意见识别**（全部条件同时满足）：用户消息 + 正文含「的意见」+ mentions 含 ≥1 非用户成员 + 正文命中已知交付件名（全名或去扩展名主干，取最长命中）；
   - **配对**：意见 → 会话序内其后**首个**「同作者 + artifacts 含同路径」的成员消息；配对成功 → 变更卡对应文件行尾角标「回应了你的意见」（title 携意见摘要）；
   - **未闭环** = 未配对意见（锚定条计数）；用户可「标记已满意」本地排除（sessionStorage `ma:m44-satisfied:<sessionId>`，仅本地、不进导出）；
   - 低置信（缺任一条件 / 作者或文件不匹配）→ **不展示、不计入**（宁可漏报不误报）。
4. **数据订阅**：变更卡经 `useSceneMessages`（500ms 节流 + 流式冻结）派生会话级闭环；角标仅取「本消息是否被配对为回应」——不做卡片间共享状态。

## 理由

- **卡族合并（ArtifactRow 扩展）**：同一份「交付件行」在三种语境（消息交付 / 变更 / 收尾清单）呈现不同徽章——扩展两个可选项优于再造一张卡（避免样式与交互双实现）；
- **意见识别从严**：闭环统计将暴露给用户（未闭环计数、签收区），误报的代价远高于漏报——「的意见」短语 + 显式 @ + 交付件名命中三条件把假阳性压到最低；「标记已满意」提供用户侧兜底（原案要求）；
- **模板带全名**：草稿即含文件名，用户发送后解析端无需猜；主干匹配仅作人工手写输入的容错；
- **不做内联 Diff**：包体与双实现双重成本（ADR 0079 已否决「聊天内联完整 Diff」同族）；vN + 作者 + 一键跳转已覆盖「这条消息改了什么、改到第几版」。

## 被否决的方案

- **逐变更卡拉取版本 diff 统计（+12/−3）**：每卡 N 次请求且长会话卡数不可控；原案已允许降级；
- **意见识别放宽（只要 @ 成员 + 提及文件名 / 只要「的意见」）**：假阳性直接污染未闭环计数与签收统计；
- **闭环配对允许「同文件不同作者也算回应」**：协作链路中他人顺手修改会被误判为回应——作者匹配是信心底线；
- **变更卡独立于 ArtifactRow 另写一套行渲染**：与 DEV-2/收尾清单三处漂移；
- **提意见直发（不写草稿）**：违背 ADR 0064 统一回填语义（用户确认后才发送）。

## 边界与失效条件

- 写类工具集合（write_file / apply_patch / edit_file）为变更语义的判定面——新增写类工具须同步 `WRITE_TOOLS`；
- 闭环为**启发式派生**：识别规则与模板即契约（单测覆盖正例与三类负例：无 @ / 无「的意见」/ 未命中交付件）；真实输出偏离模板 → 不配对（宁缺毋滥）；
- 未闭环计数上限呈现 3 条（面板内），完整意见在消息流；「标记已满意」仅本地（会话删除清理随浏览器存储策略）；
- 若未来引入服务端意见/评审实体（结构化 opinions），本 ADR 的文本派生口径随之退役。
