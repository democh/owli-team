# REST 接口设计手册

接口是**给调用方用的契约**：人可推断、机器可校验、错误可修复。设计的目标不是「能跑」，而是「三个月后没人记得它时依然能用」。

## 设计步骤

1. **明确资源与操作**：先写「名词 + 方法」清单，再定路径——资源是名词，动作用 HTTP 方法表达；
2. **补全四件套**：每个端点写清入参 / 出参 / 错误码 / 幂等语义，缺一不算完成；
3. **产出接口表交付**：评审通过后再进入实现；实现中发现缺口回流改表（文档为准）。

## 资源与命名

- 路径用**复数名词**：`/api/sessions/:id/runs`；不在路径里塞动词（`/getUser` ✗）；
- 嵌套层级 ≤2 层；更深的从属关系用查询参数或独立资源；
- 命名用业务语言（`customer_id` 而非 `cid`）；同一概念全站同名；
- 批量操作显式：`POST /api/items/batch`，不做「传数组就是批量」的隐含约定。

## 请求与响应约定

- 统一错误响应 `{ error: string }`，文案面向调用方可读（说「怎么改」，不说「出错了」）；
- 列表接口默认按 `updatedAt` 降序；分页参数统一 `page / pageSize`（或 cursor 游标）；
- 幂等：重复提交语义明确（POST 创建需支持去重键或返回既有资源）；
- 时间戳统一 ISO 8601 字符串；金额与比例注明单位与精度；
- 字段类型与格式显式（枚举取值穷举、默认值写明）；可选字段缺省等于什么必须定义。

## 错误码设计

- 语义分段：参数错误 400 / 未认证 401 / 越权统一 **404**（不泄露资源存在性）/ 冲突 409 / 系统错误 500；
- 不用 200 包错误体；业务拒绝与系统故障分开表达（前者可修复，后者可重试）；
- 每个错误码给一句「调用方该怎么办」（改参数 / 先登录 / 稍后重试 / 联系支持）；
- 错误体不暴露堆栈、SQL 与内部路径。

## 兼容与演进

- 字段**只增不改义**；破坏性变更走新版本（`/v2/` 或新字段 + 弃用期）；
- 废弃字段标注弃用时间与替代方案，过渡期内双写；
- 变更同步更新文档与全部调用方——口头通知不算同步。

## 接口表模板

| 方法 | 路径 | 入参 | 出参 | 错误 |
| ---- | ---- | ---- | ---- | ---- |
| GET | /api/example | - | `{ items }` | 500 |

- 每个端点至少覆盖四类响应：**成功 / 参数非法 / 权限不足 / 幂等重复**；
- 关键端点附示例请求与响应（真实字段值，不写占位符）。

## 常见的坑

- **GET 无分页**：列表长大后一次拉全表——首版就给分页参数；
- **错误体各自为政**：一半端点返回 `{ error }`、一半返回 `{ message }`——统一契约；
- **业务拒绝当 500**：余额不足是 409 不是 500——错误语义分级关乎重试策略；
- **越权返回 403**：403 确认了「资源存在但你没权限」——探测面，统一 404；
- **时间格式混用**：一会儿时间戳一会儿字符串——全站 ISO 8601；
- **隐式批量**：接口悄悄支持数组入参但文档没写——显式定义批量端点。

## 工具接入口径

- 先读现状再设计：`read_file` / `grep` 摸清既有路由与命名习惯，保持全站一致；
- 行为核实：HTTP 语义 / 标准头拿不准时先 `web_search` 查规范再定；
- 验证：实现后用 `run_command` 跑类型检查与接口测试（如可用），把「命令 + 结果」写进说明。

## 协作衔接

- 与 `system-design` 的「接口契约」段同源：架构文档引用本文档的接口表；
- 变更第一时间同步前端与测试侧；联调差异以文档为准更新，不各自改口；
- 安全敏感端点（鉴权 / 限流 / 敏感数据）配合 `code-review` 与安全评审。
