# MCP 服务构建手册

MCP server 是「给 Agent 用的 API」：调用者没有上下文、只会读工具描述。所以**描述即文档、schema 即契约、错误即提示**。

## 设计步骤

1. **划工具边界**：一个工具 = 一个动词 + 一个资源（`search_issues`、`create_invoice`）；不要做「万能工具」。工具数量 3–10 个为佳，超过就合并同类项。
2. **写描述**：description 必须包含「做什么、什么时候用、有什么限制」三要素——Agent 靠它决定调不调。
3. **定 schema**：参数逐个给类型、格式、枚举与默认值；必填项从少不从多；命名用业务语言（`customer_id` 而非 `cid`）。
4. **定返回**：结构化返回（字段显式）优于长文本；列表接口必须分页（`limit` + 游标或偏移）；大对象给摘要 + 详情指针。
5. **定错误**：区分「参数错误 / 业务拒绝 / 系统故障」三类，各自返回可执行的修复提示（「日期格式应为 YYYY-MM-DD」）；不暴露堆栈与内部路径。
6. **安全与密钥**：凭据走环境变量 / 密钥文件，绝不写进代码、日志与返回体；写操作工具默认最小权限，危险动作加确认参数（如 `dry_run`）。
7. **测试**：每个工具给正常 / 边界 / 错误三类用例；手测清单跑一遍：描述能否被正确理解、schema 校验是否拦截坏输入、错误提示是否可执行。

## 工具定义模板

    name: search_invoices
    description: 按客户与时间段检索发票。当需要核对账务或对账时使用；仅支持最近 24 个月。
    input:
      customer_id: string（必填）客户编号，如 C-1024
      from / to: string（必填）日期 YYYY-MM-DD
      status: enum[draft, sent, paid]（可选）
      limit: number 默认 20，最大 100
    output:
      items: [{ id, amount, currency, status, issued_at }]
      next_cursor: string | null
    errors:
      - INVALID_DATE: 日期格式错误 → 提示应使用 YYYY-MM-DD
      - NOT_FOUND: 客户不存在 → 提示先调 search_customers

## 实现纪律

- 传输与协议层用官方 SDK（TypeScript / Python），不自造握手；长任务超出协议超时前必须分页或异步化。
- 每一次调用都留审计日志（谁、什么时候、调了什么、结果如何），日志脱敏。
- 幂等：写操作带幂等键（请求 ID），重试不产生重复副作用。
- 本地与本仓集成：服务注册与凭据由用户配置（如 MCP 配置文件 / 连接配置），不硬编码。

## 检查清单

- [ ] 工具边界单一；命名是「动词 + 资源」
- [ ] 描述含「做什么 / 何时用 / 限制」
- [ ] schema 类型完整、必填克制、示例真实
- [ ] 列表分页；返回结构化；错误三类可修复
- [ ] 密钥不入代码 / 日志 / 返回；写操作最小权限
- [ ] 每工具三档用例通过

## 常见的坑

- **万能工具**：一个工具干所有事（`do_anything`）——Agent 无法判断何时调用，参数组合爆炸；
- **描述敷衍**：description 只有一句「查询数据」——Agent 不知道限制与前置条件，误调用频发；
- **返回大杂烩**：列表不分页、返回整坨 JSON——塞爆上下文且拖慢响应；
- **错误裸奔**：把堆栈 / 内部路径直接返回——安全暴露且对 Agent 不可修复；
- **密钥泄漏**：凭据写进代码 / 日志 / 返回体——一次泄漏全盘重来；
- **无幂等**：写操作重试产生重复副作用——必须带幂等键（请求 ID）。
