# 公司沟通文稿手册

一切沟通稿只服务一件事：**让读者在 30 秒内知道发生了什么、与自己有什么关系、需要做什么**。

## 通用结构（任何类型都先套这三段）

1. **结论 / 变更点**：一句话，放最前面（不含背景铺垫）。
2. **影响与相关人**：谁会受影响、影响是什么。
3. **行动与期限**：需要谁、在何时、做什么。

## 类型矩阵

| 类型 | 结构要点 | 禁区 |
| --- | --- | --- |
| 公告 / 通知 | 变更点 → 生效时间 → 对谁有影响 → 找谁 | 不写「特此通知」类废话 |
| 进展更新（3P） | Progress 已完成 / Plans 接下来 / Problems 阻塞与求助 | 不报流水账，只报变化 |
| 周报 | 三段：结果指标 → 本周关键动作 → 下周计划与风险 | 不写过程细节 |
| FAQ | 一问一答；答案给动作或明确「暂无定论 + 何时更新」 | 不含糊其辞吊胃口 |
| 事故 / 故障通报 | 现状 → 影响范围 → 处置动作 → 下次更新时间点 | 不猜测原因、不甩锅 |
| 对外更新信（投资人 / 客户） | 本期亮点数字 → 关键动作 → 下期承诺 | 不夸大、不藏坏消息 |

## 语气纪律

- **结论先行**：第一段就是答案；背景放在后面或折叠（`::: details`）。
- **主动语态、动词具体**：「周三前提交报价」而不是「请尽快处理相关事项」。
- **少形容词**：「显著提升」改为数字；无数字就不说。
- **一个动作**：每份文稿最多一个核心请求；多个请求清单化。
- **敢说坏消息**：坏消息写清楚 + 补救计划 + 已采取动作，不淡化。
- **人称一致**：内部用「我们」，对外用「我们 / 贵方」；不混用「你」「您」。

## 邮件形态（mail 容器）

对外或正式邮件用 Markdown 扩展渲染成邮件卡：

    ::: mail
    收件人: chen@example.com
    抄送: team@example.com
    主题: <一句话结论式主题>
    :::

    正文：结论 → 影响 → 行动 → 期限；结尾附联系人。

- 主题行 = 结论句，不含「关于…的通知」式空话。
- 时间表达用 `date_calc` 核算（如可用）；「本周三」一律写成具体日期。

## 检查清单

- [ ] 第一段就能回答「与我何干」
- [ ] 每个数字有来源；每个承诺有期限与责任人
- [ ] 只有一个核心行动请求（或已清单化）
- [ ] 无内部黑话；新同事读完能看懂
- [ ] 敏感信息（金额 / 人 / 客户名）已确认知悉范围

## 工具用法

- `write_file` 落盘；公告 / 更新类统一放 `docs/`。
- `::: mail`（邮件卡）、`::: timeline`（节奏与时间点）、`::: kpi`（数据更新）按需组合。
- 发送类事项提醒：文稿 ≠ 已发送，需注明「待确认发送渠道与时间」。

## 输出约定

- 命名 `docs/<类型>-<主题>-<日期>.md`（如 `docs/公告-系统维护-2026-09-18.md`）。
- 文末标注：草稿状态、建议发布渠道、发布前需谁确认。
