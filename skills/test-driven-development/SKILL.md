# 测试驱动开发（TDD）

TDD 的核心不是「先写测试」，而是**用小步反馈换取设计信心**：每写一行实现代码前，先有一个因它而由红转绿的测试。

## 触发场景

- 实现新功能、修复 bug、重构既有逻辑（后端与服务端逻辑优先适用）；
- 代码评审时发现「无法验证」的改动——先补行为测试再继续；
- 交接与复现：任何需要向他人证明「这个改到过什么」的场合。

## 何时用 / 何时不用

- **用**：新增函数与模块、修 bug（先写复现测试）、重构前补行为网、有明确输入输出的逻辑；
- **不用**：探索性原型（第一次写清需求时）、纯样式调整、一次性脚本——但原型定型后必须补测试；
- **灰区**：UI 视觉与交互断言交给 `webapp-testing` / `ui-review` 的技能口径，TDD 专注可判定的行为。

## 红-绿-重构循环

1. **红**：写一个最小失败测试——先跑一遍，确认它**因为预期原因**失败（不是因为拼写错误或环境问题）；
2. **绿**：写最少量的实现让测试通过——不为未来需求提前设计；
3. **重构**：在全部绿色状态下整理实现（提取函数、去重、改名），每步小改后复跑测试；
4. **提交粒度**：一个循环一个逻辑单元；循环超过 15 分钟没转绿，说明测试太大——拆小。

## 写测试的口径

- **一测一事**：每个测试只断言一个行为；测试名说清「在什么条件下、期望什么」；
- **三件套结构**：准备（Arrange）→ 执行（Act）→ 断言（Assert），段间空行分隔；
- **确定性**：不依赖真实时间、网络、外部服务与执行顺序；该注入的用注入（对齐本仓「共享测试替身」模式）；
- **可读性**：断言失败信息要能直接读出「期望 X、实际 Y」；
- **边界优先**：空输入、单元素、极值、重复调用、失败路径——比快乐路径更值钱。

## 断言质量检查（防假绿）

- 测试**真的会失败吗**：写完绿色测试后，临时破坏实现（或回退一行），确认测试转红，再恢复；
- 禁止「只断言不抛错」：`expect(x).toBeTruthy()` 类弱断言换成语义断言；
- 测试内的 mock 不得断言实现细节（调用次数即内部实现）——断言行为与输出；
- 快照类断言必须人工审阅一次再入库，防止把错误快照固化。

## 修 bug 的 TDD 变体

1. 先用最小输入**复现** bug，测试转红（记录失败信息）；
2. 再修实现，测试转绿；
3. 补一个相邻边界测试，防止同类问题换位置再犯；
4. 提交信息写清「修复了什么行为」。

## 与工程纪律的衔接

- 先读后写：动手前读清相关实现与既有测试，沿用既有测试风格与夹具；
- 最小 diff：实现只改满足测试所需的代码，不顺手重构无关部分（重构单独一轮）；
- 验证闭环：合并前跑**相关套件 + 全量回归**——只跑新测试不算闭环；
- 若可用 `run_command`：用它跑测试套件并贴结果；不可用时给出精确的本地命令与预期输出，请用户执行后回报。

## 检查清单与反模式

- 交付前核对：① 每个新行为都有先红后绿的测试？② 破坏实现能转红（防假绿）？③ 测试无时间/顺序依赖？④ 相关套件与全量回归都过？⑤ 测试名能当行为文档读？
- 反模式：先写完实现再补测试（补不出真正先红的证据）；为了通过而放宽断言；测试里断言 mock 调用次数；一个测试塞十个断言；跳过验证直接说「应该没问题」。
