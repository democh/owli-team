# 实施计划编写手册

计划写给**没看过这份代码、也没参与讨论**的执行者（人或 agent）。他懂这门语言、会按项目风格写代码；他不知道的是**你定下的事**：改哪些文件、接口叫什么、取规格里的哪个值、哪条测试证明这一步成立。计划就是把「你定下的事」写死。

DRY、YAGNI、TDD、小步提交。

## 使用流程

1. **读规格与代码**：规格里的约束逐条抄下来，不要转述；先看既有目录结构与相邻实现，计划要长在现有形状上。
2. **先划文件结构**：确定「谁负责什么」再拆任务——文件边界一改，任务全废。
3. **拆任务**：每个任务自带测试循环、能被单独验收。
4. **写步骤**：一步一个动作，每步都有可判定结果。
5. **自检**：规格覆盖、步骤粒度、命名一致、风险清单。
6. **落盘并请人复核**：`write_file` 写 `plans/YYYY-MM-DD-<feature>.md`，`write_todos` 同步成执行清单，再 `handoff` 给执行者。

## 范围检查

规格若含多个互不依赖的子系统，先拆成多份计划（一份一个子系统），每份都能独立交付「能跑、能测」的软件。别用一份巨型计划糊过去。

## 文件结构（先于任务）

- 一个文件一个明确职责，接口清晰、边界可描述；
- 宁小勿大：一次能读进上下文的文件，改动才可靠；
- 一起变的东西放一起；按职责拆，不按技术分层拆；
- 存量代码先跟随既有模式；确实臃肿的文件可以在计划里附带拆分，但不要顺手重构无关部分。

## 任务与步骤粒度

**任务的边界**：能独立跑完一次测试循环、值得让评审者单独点头的最小单元。把配置、脚手架、文档折进需要它的那个任务；只在「评审者可能否掉 A 却通过 B」处切开。

**步骤的边界**：一个动作 + 一个可检查结果。

- 写失败的测试 → 跑，确认它因预期原因失败 → 写最小实现 → 跑，确认通过 → 提交。

一个步骤写成「注意质量」「处理边界」这种无法执行的话，等于没写。

## 计划模板

```markdown
# <特性名> 实施计划

**目标**：一句话说清这次要建成什么
**架构**：2–3 句方案要点（模块划分与关键取舍）
**技术栈**：涉及的关键技术 / 库 / 版本下限
**规格**：<规格文件路径>（执行者要同时读规格）

## 全局约束
- 版本下限、依赖限制、命名与文案规则、平台要求——逐条照抄规格里的原值

## 风险与关注点
- 规格隐含、但没有任务测试覆盖的输入 / 失败模式，按「最可能伤人」排序，每条一行

## 任务
### 任务 1：<模块名>
**文件**：新建 `<路径>` / 修改 `<路径>:<行>` / 测试 `<路径>`
**接口**：消费 <上游签名>；产出 <下游依赖的函数名、参数与返回类型>
- [ ] 步骤 1：写失败测试（贴出断言与规格里的具体值）
- [ ] 步骤 2：跑测试，确认失败（命令 + 预期报错）
- [ ] 步骤 3：实现 `<签名>`（只写签名与不显然的算法）
- [ ] 步骤 4：跑测试，确认通过（命令 + 预期输出）
- [ ] 步骤 5：提交（文件清单 + 提交信息）
```

## 一步该写多少

| 步骤类型 | 必须包含 | 不要包含 |
| --- | --- | --- |
| 测试步骤 | 测试名 + 断言 + 规格原值 | 整段实现 |
| 代码步骤 | 精确签名、所在文件、规格钉死的值 | 签名和测试已决定的函数体 |
| 验证步骤 | 命令 + 「什么输出算通过」 | 「自行确认」 |
| 引用其他任务 | 「按任务 N 的接口块」 | 重复抄任务 N 的代码 |

计划比它描述的代码还长，就是在替执行者写代码；满篇「TBD / 处理边界 / 补测试」的计划，则是什么都没决定。两种都要在自检里抓。

## 自检清单（自己跑，不委派）

- [ ] **规格覆盖**：每节需求都能指到一个任务，指不到的补任务；
- [ ] **步骤扫描**：每步只让执行者写「唯一合理的一件事」，不多不少；
- [ ] **命名一致**：后面任务用的函数名、字段名与前文定义一致（`clearLayers` 写成 `clearFullLayers` 就是缺陷）；
- [ ] **风险清单**：每条风险都能指到「哪个任务的哪条测试钉住它」；
- [ ] **比例**：计划篇幅不该是规格的好几倍；代码块占大头就改成签名 + 测试名。

## 交接

- 计划落到 `plans/YYYY-MM-DD-<feature>.md`；`write_todos` 建任务级清单（5–9 条），步骤留在文件里；
- `handoff` 时只传三样：计划路径、全局约束、本次要做的任务编号；
- 执行方式二选一：**串行自做**（逐任务实现、逐任务验证）或**按场景链分派**（分给对应角色，每个任务独立验收后再放下一个）；
- 请需求方先看计划、确认后再动手；确认内容要落到「目标 / 范围 / 验收方式」三句上。

## 常见的坑

- **计划里塞实现**：执行者变复读机，评审无从下手；
- **任务跨多个不可分验证点**：失败了不知道退回哪；
- **接口留给执行者猜**：跨任务命名不一致，联调时才炸；
- **规格值靠转述**：「大约 30 秒超时」——抄原值；
- **计划不落盘**：只在对话里说，`handoff` 之后没人拿得到。
