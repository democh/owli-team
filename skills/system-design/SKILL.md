# 系统设计手册

架构文档的价值在于**把权衡写下来**：选了什么、放弃了什么、为什么。没有权衡记录的方案不是设计，是通知。

## 文档骨架（按序）

1. **问题与约束**：要解决什么问题；非功能约束（性能 / 成本 / 团队规模 / 期限）——约束决定方案。
2. **现状与范围**：改动涉及哪些模块；明确不改什么。
3. **方案总览**：一张 mermaid 图（组件 + 数据流），配 3–5 句文字说明；图与文字必须一致。
4. **关键决策**：每个决策一段——背景 / 选项 / 选择 / 理由 / 代价；重大决策单独落 ADR。
5. **数据模型**：实体与关系、关键字段、索引与约束；迁移方案（如改结构）。
6. **接口契约**：对外接口逐个写——方法 / 路径 / 入参 schema / 返回 / 错误码；与 `api-design` 规范一致。
7. **失败模式与降级**：依赖挂了怎么办 / 超时怎么办 / 数据不一致怎么恢复；每项给可观测信号。
8. **演进路线**：现在做什么（MVP）→ 什么条件下做下一步；不做过度设计，但预留接缝。

## 技术选型三问（每个选项都要回答）

1. 它解决的核心瓶颈是什么？
2. 把它换掉需要多大代价（被锁定程度）？
3. 团队现在有人会运维它吗？

- 新引入的组件必须回答三问；答不上就先用现成方案。
- 优先「无聊的技术」：成熟、文档多、团队熟悉；创新留给核心业务差异点。

## 评审清单（设计评审时逐条过）

- [ ] 约束与非目标明确；范围无暗扩张
- [ ] 图（mermaid）与文字一致，无「幽灵组件」
- [ ] 每个关键决策有理由与代价；有 ADR
- [ ] 数据模型有约束（唯一 / 外键 / 索引）与迁移方案
- [ ] 接口有错误码与超时约定
- [ ] 至少 3 个失败模式有降级路径与信号
- [ ] 演进路线含触发下一步的条件

## 表达纪律

- 容量与性能给估算过程（QPS × 单次成本），不给「应该够用」。
- 图用 mermaid 代码块（在界面中直接渲染）；对照取舍用 `::: cols`，决策点用 `::: option`。
- 术语表：跨模块出现的名词统一定义，避免同词异义。

## 工具用法

- 先读现状：`search_text` / `read_file` / `glob` 摸清现有模块，再画图设计——不凭印象改架构。
- 落盘 `write_file`；相关决策同步提请 ADR（与项目已有 ADR 目录规范一致）。
- 涉及 git 工作流（如 worktree / 分支策略）用 `git_status` / `git_log` 核实现状再写。

## 输出约定

- 设计文档：`docs/design-<模块>.md`；附 mermaid 架构图与决策记录。
- 重大决策提交 ADR；文档内引用 ADR 编号，不复述全文。
