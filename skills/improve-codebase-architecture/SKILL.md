# 存量架构改进扫描

目标不是「重构一遍」，而是找出**加深机会**：把浅模块变成深模块，让改动与缺陷收敛到一处。判据始终是**可测试性**与**可导航性**——新人和 agent 能不能顺着一条边界把事弄懂。

本技能使用 `codebase-design` 的词汇（模块 / 接口 / 实现 / 深度 / 接缝 / 适配器 / 杠杆 / 局部性）；需要展开时先 `load_skill` 加载它。

## 使用流程

1. **定扫描范围**（先 YAGNI，再扫描）；
2. **读领域与决策**：项目术语表（`GLOSSARY.md` 或同类文档）、`docs/adr/` 里与目标区域相关的决策；
3. **走查摩擦点**：只记「卡住的地方」，不套检查表；
4. **出候选卡**：每个候选给出文件、问题、方案、收益、前后对比、推荐强度；
5. **落盘 + 可视化**：写自包含 HTML 报告（本工作区 `reports/architecture-review-<日期>.html`）；
6. **选一个深挖**：由需求方挑候选，再逐个决策点过一遍，必要时补 ADR。

## 第 1 步：定范围

加深模块的回报来自「以后改它更容易」，所以**优先看最近在变的代码**。

- 需求方已指名方向（某模块、某子系统、某个痛点）→ 直接采纳，跳过推断；
- 没指名 → 用 `run_command` 跑 `git log --oneline -50` 找热点（反复出现的文件与目录），让热点决定先看哪；
- 改动分散、没有明显热点 → 扩大范围，但只挑 2–3 个候选，不做全仓普查。

## 第 2 步：读领域与决策

- 术语表决定「模块该叫什么」：用业务术语命名，不用内部类名；
- `docs/adr/` 已经拍过的方案不重复提；确实要翻案的，必须在候选卡上显式标注「与 ADR-XXXX 冲突，理由是…」；
- 没有术语表 / ADR 就先按现状用词，产出里记一句「术语表缺失」即可，不顺手补全套。

## 第 3 步：找摩擦（命中即记）

- **概念跨文件**：理解一件事要在 4 个以上小文件之间来回跳；
- **浅模块**：接口几乎和实现一样宽（大量 getter / 一层转发 / 参数即内部字段）；
- **为测试而抽的纯函数**：函数抽干净了，真正的缺陷藏在调用方与装配顺序里，没有局部性；
- **耦合泄漏**：本该在接缝后面的细节（SQL、协议、第三方字段）漏到上层；
- **不可测**：只能起完整服务才能碰到的逻辑；测试要准备十几个前置状态；
- **重复装配**：同一串初始化在 N 个入口各写一遍，改一处必漏。

每个可疑对象都过一遍**删除测试**：删掉它，复杂度是消失（直通层）还是在调用方重新长出来（真模块）？只有「重新长出来」才值得加深。

## 第 4 步：候选卡字段

| 字段 | 要求 |
| --- | --- |
| 文件 | 涉及的模块与文件，`路径:行` 形态 |
| 问题 | 一句话，说清哪种摩擦（用词汇表用词） |
| 方案 | 一句话，「接口收缩成什么、实现吸收什么」 |
| 收益 | 杠杆（N 个调用点）/ 局部性（改一处）/ 测试面（一个接口），3–5 条 |
| 前后对比 | 并排图或两段伪结构；不要用一段话解释图 |
| 推荐强度 | `强` / `值得探索` / `仅存假设` |

**不要在候选阶段就设计接口**——先让需求方挑方向，接口等选中后再谈。

## 第 5 步：报告

- 位置：本工作区 `reports/architecture-review-<YYYY-MM-DD>.html`（一次一份，不覆盖旧报告）；
- 形态：单文件自包含；Tailwind 与 Mermaid 走 CDN；图能说明问题就不要写段落；
- 结构：页头（仓库名 + 日期 + 图例）→ 候选卡（按推荐强度降序）→ 「先做哪个」一段；
- 图例固定四样：实线框 = 模块，虚线 = 接缝，红色箭头 = 泄漏，深色厚框 = 深模块；
- 只有两个脚本（Tailwind、Mermaid），其余静态；不许内嵌业务代码或交互逻辑；
- 落盘后用 `write_file` 交付绝对路径，并说明「先看哪张卡」。

若环境无法打开 HTML（纯终端），改为同结构的 Markdown 报告 `reports/architecture-review-<日期>.md`，图用 mermaid 块代替。

## 第 6 步：选中之后

按「约束 → 依赖 → 加深后的接口形状 → 接缝后面放什么 → 哪些测试能活下来」逐个过决策点：

- 新出现的业务概念 → 补进术语表（没有就按需新建）；
- 需求方基于长期理由否掉某个候选 → 提议记一条 ADR，避免下一轮重复提；
- 要比较多套接口 → 每套各写一页「接口 + 调用方代价 + 测试面」，并列比较后择优，不要口头二选一；
- 定稿后交给 `writing-plans` 拆任务；改造范围大时先落一条 ADR 再动手。

## 输出约定

```markdown
## 架构扫描：<范围>（<日期>）
- 热点依据：<recent commits / 用户指名>
- 候选 1：<名字>（强）— <问题一句话> → <加深一句话>
- 候选 2：…
- 建议先做：<候选名>，因为 <一句理由>
- 报告：reports/architecture-review-<日期>.html
```

## 常见的坑

- **全仓普查**：没有热点依据就扫全部代码，产出一堆没人会做的候选；
- **把重构当目标**：说不清杠杆与局部性收益，就不该进候选；
- **候选阶段就写接口**：需求方还没选方向，接口设计全白做；
- **无视 ADR**：翻案不标注，等于让评审重打一次架；
- **报告写成长文**：图能说清的写成三段话，没人看完；
- **扫描完不动手**：没有「先做哪个 + 交给谁」的结论，报告只是装饰。
