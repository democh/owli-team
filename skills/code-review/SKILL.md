# 代码评审手册

评审的目标是**拦住真实缺陷**，不是刷存在感。只报高信号问题：能阻止线上事故 > 影响维护成本 > 风格偏好。

## 评审流程

1. **明确范围与意图**：先看改动（`git_diff` / `read_file`），用一句话写出「这次改动应该做什么」——评审的第一件事是判断「做的是不是这件事」；
2. **快扫结构**：文件 / 模块划分、入口与数据流，建立整体印象后再逐行；
3. **逐组过清单**（下节六组），按影响排序记录问题；
4. **输出结论**：问题列表（严重度 / 位置 / 说明 / 修法），只列 3–8 条最有价值的，避免噪音淹没重点。

## 六组检查清单

**① 正确性**

- 边界条件：空值、超长、恰好临界、并发、时区、浮点精度；
- 错误路径不被吞掉：失败分支有处理或明确上抛，不静默 `catch {}`；
- 状态一致性：多步更新中途失败的回滚 / 补偿；异步竞态（并发写、双提交）。

**② 安全**

- 输入校验与注入面：SQL / 命令拼接 / 路径穿越 / XSS / 模板注入；
- 鉴权与越权：资源归属校验（越权访问返回 404 而非 403）、敏感操作二次确认；
- 敏感信息：密钥不入代码与日志；错误信息不泄露内部结构。

**③ 性能**

- N+1 查询、循环内 IO、无界集合全量加载；
- 大对象拷贝与不必要的序列化；前端：无谓重渲染、大列表未虚拟化。

**④ 可维护性**

- 命名与既有代码一致；复用已有工具函数而不是重复实现；
- 函数是否过长（>80 行为信号）；嵌套是否超过 3 层；
- 魔法数字 / 硬编码路径 / 复制粘贴的分支；注释解释「为什么」而不是「是什么」。

**⑤ 测试**

- 改动是否带测试（或说明为何不适用）；断言是否可判定（具体值 / 状态）；
- 可测性：纯函数优先、副作用集中；测试命名能看出失败含义。

**⑥ 兼容与迁移**

- API / 字段 / 错误码变更是否同步文档与调用方；废弃项是否有过渡期；
- 数据迁移的可逆性与回滚路径；功能开关（默认关 / 灰度）与降级手段。

## 严重度口径

- **阻断**：会导致错误结果 / 数据损坏 / 安全漏洞 / 线上不可用——不修不能合；
- **建议**：可维护性、性能、一致性显著受损——应在本次或近期修；
- **提示**：风格与优化机会——采纳与否由作者决定，不反复纠缠。

## 输出模板

```markdown
## 评审结论：通过 / 有条件通过 / 不通过
| 严重度 | 位置（文件:行） | 问题 | 修法（可直接应用） |
| --- | --- | --- | --- |
| 阻断 | src/api.ts:42 | 越权：未校验资源归属 | 在查询条件加 owner_id = 当前用户 |
```

- 每条问题必须给「定位 + 为什么错 + 怎么修」三件套；给不出修法的条目降级为「提问」；
- 不确定的假设显式标注（「如果 X 成立则此条成立」），不把口味当规范。

## 评审纪律

- **只评审，不顺手改**：修改交实现者执行；确需示范时给最小 diff 片段，不提交；
- 对事不对人：说「这个分支漏了空值」，不说「你怎么又忘了」；
- 先肯定设计意图再提问题，避免作者防御性解释掩盖真问题；
- 高信号优先：一次评审不要超过 8 条，风格类问题集中成一条附在末尾；
- 复核闭环：修复后先验证原问题场景，再抽查相邻路径，确认修复未引入新问题。

## 工具用法

- 定位：`git_diff`（看改动范围）/ `read_file` / `grep`（找调用方与同类实现）/ `search_text`（找既有规范用法）；
- 验证：`run_command` 跑测试 / 类型检查佐证评审结论（如可用）；
- 前端走查配合 `ui-review`，安全深挖配合 `red-team`，测试设计配合 `test-plan`。
