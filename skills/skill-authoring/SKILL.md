# 技能编写手册

技能是「按需加载的专业方法论」：平时只暴露 name + description 两行元数据，被 load_skill 命中后整篇注入上下文。写法围绕两件事——**能被想起来**（description）与**读完就能干**（正文）。

## 编写流程

1. **先定两问**：这个技能让谁、在什么场景下、把什么事做对？只写「能力」不写触发，等于不会被加载。
2. **查重**：先看既有 `skills/` 目录；若能改造旧技能，优先改造而非新建。
3. **起草全文**：按下方结构写 `skills/<name>/SKILL.md`。
4. **自测触发**：假设用户只说场景（不提技能名），description 能否让人想起它？
5. **跑校验**：`npm run check:skills`（name 唯一且与目录名一致、description 非空；附**行数质量报告**——正文 ≥60 行，CI 已启用 strict 门禁）；技能库按 mtime 热更新，落盘即生效，无需重启。

## Front-matter 规范

```yaml
---
name: <与目录名完全一致>
description: <能力一句话>：<何时使用（触发场景与关键词）>
tags: [<英文小写>, <单数名词>]
---
```

- description 是唯一入口，宁可写得主动：既说做什么，也写清「什么时候想起我」。
- tags 用于分类检索，2–4 个即可。

## 正文结构（推荐）

    # 标题
    ## 使用步骤 / 工作流     ← 有序步骤，可执行
    ## 检查清单 / 模板       ← 表格、清单、可复制的骨架
    ## 工具用法              ← 写到具体工具名与参数形态
    ## 输出约定              ← 交付件命名 / 落点 / 格式

- 长度 60–150 行为宜；接近 300 行应考虑拆分主题。
- 只引用本仓真实的工具与 Markdown 容器语法，参数形态以工具描述为准，不凭空发明。
- 祈使句为主，解释「为什么」而不是堆「必须」；给模板优于给形容词。

## 质量清单

- [ ] description 含触发场景与关键词，不与其他技能撞车
- [ ] 步骤可执行，换个人照做也一致
- [ ] 引用的工具 / 容器真实存在（对照工具清单与 Markdown 扩展）
- [ ] 有输出约定（交付件名与格式）
- [ ] `npm run check:skills` 通过

## 反模式

- 把百科资料搬进来——技能是做法，不是资料库。
- 引用不存在的工具或拍脑袋的参数名，加载后无法执行。
- 与 AGENT.md 职责重复表述——职责讲「我是谁」，技能讲「怎么做」。
- 单文件塞多个不相关主题；应拆成多个目录，各自保持单一职责。

## 常见的坑

- **description 只写能力**：没写触发场景与关键词——技能永远不会被想起加载；
- **示例造假**：引用了不存在的工具名或参数——照做直接报错；
- **过长不拆**：一篇涵盖三个主题——加载后一半内容用不上；
- **空泛步骤**：写「注意质量」这类无法执行的条目——每步都要能照着做；
- **热更新误判**：改完不跑 `check:skills`——name 与目录不一致直接加载失败；
- **分类混乱**：tags 写成中文 / 复数 / 短语——统一英文小写单数名词。
