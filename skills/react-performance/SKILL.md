# 前端性能手册

性能是体验的一部分：4 秒才可交互的漂亮界面依然是坏体验。原则：**按影响排序、先测量后优化**——别一上来就 useMemo。

## 优化优先级（自上而下，上层收益大一个量级）

1. **消除请求瀑布**（最重要）：串行依赖的调用合并 / 并行；架构支持时用 Suspense 流式渲染，不等齐全部数据。
2. **包体**：路由级动态 import；图标逐个引入（禁 barrel 引入整库）；大依赖换轻量替代；首屏不需要的组件懒加载。
3. **数据获取**：请求缓存与去重；同一页面多个往返合并；不在渲染函数里发请求。
4. **重渲染**：状态就近（谁用放谁）；订阅派生布尔而不是原始大对象；`memo` 只加在实测热点（列表行、图表）上。
5. **长列表与渲染**：虚拟化或 `content-visibility`；避免万级 DOM；图片显式宽高 + 懒加载。
6. **微观**：避免在 JSX 里新建传给 memo 组件的对象 / 函数；批量状态更新；事件处理放稳定引用。

## 感知性能（用户等的是感觉）

- 骨架屏保持结构稳定；不要白屏等数据。
- 乐观更新：先渲染预期结果，失败回退并提示。
- 加载顺序即优先级：首屏关键内容先出，次要区块后补。

## 工作流程

1. 先定位症状：首屏加载慢 / 交互卡顿 / 列表滚动掉帧——不同症状对应不同优先层级。
2. 测量或静态审查：有 `run_command`（如可用、白名单）时跑构建与产物体积分析；无则静态审查并标注「需实测确认」。
3. 每处优化写：类别 / 位置 / 影响判断 / 修法 / 预期收益（量级描述）；改动最小化。
4. 改完回看检查清单，不顺手做无关重构。

## 代码常识（高频踩坑）

- `useEffect` 依赖数组漏项 / 过频触发；订阅未清理。
- 渲染函数里创建组件（每次渲染都是新组件类型）——必须提到组件外。
- Context 值未 memo，导致全树重渲染。
- 一次 setState 可解的状态拆分过细，引发多次渲染。

## 检查清单

- [ ] 无串行请求瀑布（或已说明必须串行的理由）
- [ ] 无 barrel 整体引入；重依赖有懒加载
- [ ] memo 都有热点依据，不为「心安」而加
- [ ] 长列表有虚拟化或渲染约束
- [ ] 优化项均带位置与预期收益；需实测项已标注

## 工具用法

- `read_file` / `search_text` / `glob` 审查 import 模式、`useEffect` 依赖、`memo` 使用点。
- 改动遵循既有代码风格；优化提交不混入重命名或大面积格式改动。
- 与 `frontend-design`（视觉与交互实现）、`ui-review`（质量走查）分工：本手册只管性能。

## 输出约定

- 交付：`docs/性能优化-<模块>.md`（发现表：类别 / 位置 / 影响 / 修法 / 预期收益 + 实测计划）。
- 需要真实测量支撑时，拉 `qa`（实测）或 `devops`（构建分析，`run_command` 白名单）配合。

## 常见的坑

- **先优化后测量**：凭直觉加 memo / 拆组件——先定位症状与热点；
- **memo 泛滥**：所有组件都包 memo 但 props 每次新引用——没用的 memo 只是噪音；
- **依赖数组应付**：useEffect 漏依赖或强行禁用 lint——竞态与陈旧闭包随之而来；
- **渲染中建组件**：函数组件里定义子组件——每次渲染都是新类型，整棵子树重建；
- **桶文件全量引入**：从大库的桶文件整包引入——按文件路径逐个引入；
- **大对象进 Context**：Context 值未 memo——一次变更全树重渲染。
