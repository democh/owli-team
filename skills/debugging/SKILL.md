# 缺陷定位手册

**铁律：先复现、再定位、后修改。** 没有复现路径的修复是猜测，没有回归验证的修复不算完成。

## 第一步：症状采集（先收集一手证据，再打开代码）

- 报错原文：完整堆栈 / 错误码 / 控制台输出，不截断、不转述；
- 复现条件：环境（本地 / 预发）、账号与权限、数据前置、操作顺序；
- 时间线：什么时候开始、是否伴随最近一次改动（`git_log` / `git_diff` 看引入点）；
- 影响面：单点还是全部、是否涉及数据写入（决定止损优先级）。

工具：`browser_console`（页面报错与警告）、`run_command`（命令 / 测试输出）、`read_file` / `grep`（相关代码路径）。

## 第二步：复现与最小化

1. 先拿到稳定复现路径；复现不了就先记频率与环境差异（并发、缓存、时序、数据量），不要硬猜；
2. 最小化：逐项删除无关步骤 / 数据 / 配置，直到只剩「必要输入 → 故障」；
3. 间歇性问题：固定变量法——同一输入跑 N 次、切环境、关缓存，找触发条件；
4. **把复现路径写成步骤清单**（后续回归验证直接复用）。

## 第三步：建立证据链（假设 → 验证，而不是改一行试一下）

- 每个假设写成「因为 X，所以 Y」，并给出可判定的验证动作（看哪条日志 / 哪个查询 / 哪个断点）；
- 二分定位：注释 / 短路掉一半路径缩小范围；用 `git_log` 在提交历史里二分找引入点；
- 一次只验证一个假设；被证伪的假设也要记录（防止绕圈）；
- 数据类问题先看现状再猜逻辑：`db_schema` 核对表结构、`db_query` 只读看数据（如可用）。

## 第四步：最小修复

- 修根因，不修症状（不吞异常、不靠加大超时掩盖竞态）；
- 最小 diff：只改与根因相关的代码，遵循既有风格，不顺手重构无关代码；
- 修复处顺手补齐同源风险（同类入参 / 同类路径的边界检查），但不扩大改动范围；
- 改不动或风险过高时：给出方案 A/B 与代价，交 @用户 拍板。

## 第五步：回归验证

1. 修复前先用复现路径确认问题存在（基线）；
2. 修复后再跑一遍复现路径，确认故障消失；
3. 跑相关测试 / 类型检查 / 构建（`run_command`，如可用）；前端改动加 `browser_*` 实测；
4. 抽查相邻路径（同一函数 / 同一接口的其他调用方）确认无连带损伤；
5. 留下证据：命令输出 / 截图摘要 / 查询结果，随修复说明一起给出。

## 第六步：沉淀

- 缺陷卡：症状 / 复现路径 / 根因 / 修复 / 回归证据 / 预防建议（六项缺一不可）；
- 值得复发的坑：写进工作区文档，或用 `remember` 固化口径；
- 同类问题批量排查：同一根因往往残留多处，列清单给相关角色。

## 常见反模式

- 盲目试错：不建假设，改一行跑一下，碰巧好了就收工；
- 只看代码不跑复现：脑内推演替代真实验证；
- 修复范围蔓延：把顺手的重构混进缺陷修复（评审与回归都会失焦）；
- 把「猜中了」当「定位到了」：没有证据链，同类问题必然复发；
- 吞异常 / 加超时：让问题从「可复现」变成「偶发」，更难查。

## 输出约定

- 缺陷报告：最小复现路径 / 期望 vs 实际 / 影响面 / 严重度（阻塞 / 严重 / 一般 / 轻微）；
- 修复说明：根因 / 改动点（文件 + 行为）/ 回归证据；
- 不臆测原因：结论必须可追溯到证据（日志行 / 查询结果 / 命令输出）。
