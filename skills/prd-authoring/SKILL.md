# 需求文档手册

需求的唯一标准：**开发和测试拿着它就能开工，歧义为零**。任何「到时候再说」都是风险登记，不是需求。

## PRD 骨架（按序写）

1. **背景与问题**：谁在什么场景遇到什么问题；有什么证据（用户原话 / 数据）——没有证据的需求先标「待验证」。
2. **目标与非目标**：本次要达成什么（可量化）；**明确列出不做什么**——非目标是控制范围的闸门。
3. **用户故事**：`作为 <角色>，我想 <行为>，以便 <价值>`；每个故事配 1–3 条验收标准。
4. **验收标准**：Given（前置）– When（动作）– Then（可观察结果）三段式；结果必须可被测试观测。
5. **边界与异常**：空态 / 极值 / 并发 / 失败重试 / 权限不足 / 数据被删除，逐项给预期行为。
6. **依赖与风险**：外部依赖、接口待定项、需要谁在何时确认什么。
7. **里程碑**：范围切分（MVP / 后续）与检查点日期（`date_calc` 核算）。

## 验收标准写法对照

| 不合格 | 合格 |
| --- | --- |
| 界面友好 | 首屏加载 ≤ 1.5s；空态给出创建入口 |
| 支持导出 | 导出 CSV，含全部列；> 1 万行时分页导出并给进度 |
| 处理异常 | 网络失败时保留草稿并提示重试；重试不重复提交 |

## 纪律

- 一个故事一个行为；「并且」出现即拆。
- 形容词不进入验收标准（快 / 好用 / 美观）；全部换成可测量表述。
- 范围变更走变更记录（版本表），口头变更一律不认。
- 与实现解耦：需求写行为与约束，不写技术方案（方案交 architect）。
- 拿不准的取舍：给 `::: option` 选项卡（A/B 方案 + 推荐 + 理由），交用户拍板，不自行扩张范围。

## 交接

- 交接给 architect 时附：非目标清单、待定项、验收标准；
- 交接给 qa 时附：每条故事的测试要点（正常 + 边界）；
- 收尾检查：需求编号 ↔ 验收标准 ↔ 测试用例三向可追溯。

## 检查清单

- [ ] 每个故事有角色 / 行为 / 价值，且有验收标准
- [ ] 非目标清单非空且写清了边界
- [ ] 验收标准全部可测（无形容词）
- [ ] 异常与边界覆盖（至少：空 / 极值 / 失败 / 权限）
- [ ] 待定项有责任人 + 确认期限
- [ ] 版本表记录每次范围变化

## 工具用法

- `write_file` 落盘；`write_todos` 拆分章节任务；变更用 `edit_file` 并在版本表登记。
- 日期与里程碑用 `date_calc`（如可用）；交付呈现用 `::: option`（方案取舍）、`::: kpi`（量化目标）、`::: details`（异常明细）。

## 输出约定

- 落点 `docs/prd-<功能名>.md`；文首：一句话目标 + 状态（草稿 / 待评审 / 已确认）。
- 文末：开放问题清单 + 变更记录表。
