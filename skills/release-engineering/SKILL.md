# 发布与事故手册

两条主线：**发布要可回退，事故要有资产**（每次事故都产出一份能被执行的改进清单）。

## 变更日志（Changelog）规范

按版本组织，每版固定四节，只写用户可感知的变化：

    ## v1.4.0 — 2026-09-16

    ### Added
    - 新增数据导出（CSV，支持全部筛选项）
    ### Changed
    - 登录流程合并为一步（原两步）
    ### Fixed
    - 修复导出超 1 万行时中断的问题
    ### Removed
    - 移除旧版统计面板入口

- 版本号语义：破坏性变更升 Major、新功能升 Minor、修复升 Patch。
- 条目写「对环境的影响」，不写内部实现（「重构 util.ts」不入日志）。
- 每条含类型 + 用户语言描述；可附变更编号方便追溯。

## 发布清单（每次上线前逐条勾）

- [ ] 变更日志已更新；版本号已定
- [ ] 构建 / 测试通过（`run_command` 跑既有命令，如可用）
- [ ] 数据迁移已演练（含回滚脚本或反向迁移）
- [ ] 回滚点已记录（版本 / 镜像 / 配置快照）
- [ ] 发布后验证步骤已定义（看什么指标、点哪条路径）
- [ ] 通知相关人（时间、影响面、回滚条件）

## 灰度与回滚

- 灰度：先小范围（1 个用户 / 10% 流量），观察窗口 ≥ 15 分钟再全量。
- 回滚触发条件事先写死（错误率 / 延迟 / 关键路径失败的阈值），达到即回滚，不临时开会。
- 回滚演练：每次发布至少心里过一遍「现在怎么退回去」；无人知道退路的发布不允许执行。

## 事故响应（时间线纪律）

1. **止损优先**：先恢复服务（回滚 / 降级 / 摘流量），再查原因。
2. **全程记时间线**：什么时候发现、谁做了什么、服务状态变化——用 `::: timeline` 落盘（`date_calc` 校时，如可用）。
3. **对外通报**：现状 → 影响范围 → 处置动作 → 下次更新时间点（对齐 `comms-writing`）。
4. **无责复盘**（事后 48h 内）：

       时间线：<发现 → 止损 → 恢复 → 复盘>
       影响：<用户 / 数据 / 时长，量化>
       根因：<技术根因 + 为什么没被提前拦住>
       改进项：<每条 = 动作 + 责任人 + 期限 + 验证方式>

- 根因追到「系统为什么允许这个错误发生」，不停在「某人手滑」。
- 改进项必须可验证（指标 / 测试 / 流程检查点），否则不算闭环。

## 检查清单

- [ ] 变更日志四节齐全、版本语义正确
- [ ] 发布清单全勾；回滚点已记录
- [ ] 回滚触发阈值事先写死
- [ ] 事故时间线有起止时间与动作记录
- [ ] 改进项含责任人 / 期限 / 验证方式

## 工具用法

- `run_command` 执行既有构建 / 测试命令（仅白名单、默认关闭时改用人工清单）。
- git 工具：`git_log` 收集变更、`git_branch` / `git_commit` 参与发布流；不执行破坏性 git 操作。
- 时间线用 `::: timeline`、待办用 `write_todos`、关键数字用 `::: kpi`。

## 输出约定

- 变更日志：`CHANGELOG.md` 或 `docs/release/<版本>.md`。
- 复盘报告：`docs/postmortem-<事故名>-<日期>.md`（结构固定为上面四段）。
