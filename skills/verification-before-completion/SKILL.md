# 完成前验证手册

**核心原则：证据先于结论，永远。**

跳过验证就说「好了」，不是乐观，是谎报。本手册只做一件事：在每一句「完成」出口之前，插一道闸门。

## 铁律

```
没有当次新证据，不许说完成
```

判断标准极简：**这条结论对应的命令，本轮做过吗？输出看过吗？** 没跑过、没看过，就不许说「通过」。

## 验证闸门（五步，一步都不能省）

1. **定证据**：这句话要用哪条命令证明？（测试 / 构建 / 类型检查 / 复现原 bug）
2. **完整跑**：执行**完整**命令——不只看一个用例、不跑半截、不复用上一轮结果。
3. **读输出**：看退出码 + 完整输出，数失败条数，而不是扫一眼有没有红字。
4. **对结论**：输出能否**直接**支持这句话？不能就如实说当前状态（「跑了，还有 2 个失败：…」）。
5. **再开口**：以上都过了，才把结论说出口，并把证据附在结论后面。

跳过任一步，等于没验证。

## 什么结论需要什么证据

| 结论 | 够用的证据 | 不算证据 |
| --- | --- | --- |
| 测试通过 | 测试命令输出：0 失败（附条数） | 上次跑过 / 「应该能过」 |
| 类型 / Lint 干净 | 对应检查输出：0 error | 只跑了 lint、没跑 tsc |
| 构建成功 | 构建命令退出码 0 | lint 通过、日志「看着正常」 |
| bug 已修 | 原症状场景复跑通过 | 代码改了、看起来对 |
| 回归测试有效 | 先红后绿的实证 | 测试跑通一次 |
| 成员 / 委派任务完成 | 自己看产物与改动 | 对方回一句「搞定了」 |
| 需求已满足 | 逐条对照清单打勾 | 「测试都过了」 |

## 红旗：出现即停

- 「应该」「大概」「看起来」「理论上」开头的结论；
- 验证之前先说「好了 / 完成 / 搞定 / 完美」；
- 准备提交、`handoff`、交付，而没有当轮验证；
- 直接采信「已完成」的汇报（成员、命令摘要、上一次会话）；
- 用局部验证代替整体验证（只测一个用例就宣布全绿）；
- 「就这一次」「下次再补」。

## 常见借口对照

| 借口 | 事实 |
| --- | --- |
| 「逻辑上肯定对」 | 信心 ≠ 证据，跑一遍只要三十秒 |
| 「上次就是这么修的」 | 上次的产物不是这次的代码 |
| 「lint 过了」 | lint ≠ 编译 ≠ 测试，三者不能互替 |
| 「测试太慢」 | 慢是成本，谎报是负债 |
| 「换个说法就不算宣称完成」 | 规则管意图，不管措辞 |

## 关键模式

**测试**

```
✅ 跑 `npm test` → 34 passed / 0 failed → 「34 项全过」
❌ 「现在应该没问题了」
```

**bug 修复（含回归）**

```
✅ 复现 → 修 → 原场景复跑通过 → 撤销修复确认测试变红 → 恢复 → 再跑绿
❌ 「我加了条测试」（没验过红绿循环）
```

**构建 / 类型**

```
✅ 跑 `npm run build` 与 `npm run typecheck` → 退出码 0 → 「构建与类型检查通过」
❌ 「lint 干净，估计能构建」
```

**需求**

```
✅ 重读需求 → 列勾选清单 → 逐条对证据 → 报剩余缺口
❌ 「测试过了，这阶段完成」
```

**多成员 / 并行**

```
✅ 收到完成汇报 → 自己看产物与改动 → 独立复跑 → 再向上汇报
❌ 转述「某某说已经改好了」
```

## 与工具配合

- 取证据：`run_command`（测试 / 构建 / 类型检查 / 复现脚本）；
- 核对改动：`search_text` 找残留（TODO、占位、旧调用方），`read_file` 复核关键分支；
- 交付前：`write_todos` 把验证项列成清单逐项打勾；`handoff` 时把「证据 + 未验证项」一起写进交接口径。

## 输出约定

结论句必须长这样，缺一段就不算完成：

```
结论：<完成 / 部分完成 / 未完成>
证据：<命令> → <关键输出：条数 / 退出码 / 报错摘要>
缺口：<未覆盖的场景、未跑的检查；没有则写「无」>
```

## 与相邻技能

- 设计测试用例：`test-driven-development` / `test-plan`；
- 交付前完整走查：`code-review`；
- 上线与回滚检查：`release-engineering`。
